# The Sample Standard

What every sample in this repository ships, and the bar it meets before it is
merged. The standard is derived from [`samples/control-plane`](../samples/control-plane/),
the reference sample; where the two disagree, fix whichever one is wrong and
say so in the pull request.

A sample is a deployable demonstration of one pattern, shipped with the design
trail that explains why it looks the way it does. Samples are modular: a sample
may consume other samples, and every sample is built so that others can consume
it (§1.1). Readers should be able to deploy it, run its integration test, read
its reasoning, and take the pattern into their own system by reading the sample
directory plus the published interfaces of the samples it depends on. How the
samples fit together is in [`ARCHITECTURE.md`](../ARCHITECTURE.md).

**Terminology.** The repository is about multi-tenant *agentic applications*.
Two actor classes exist, and every sample uses these two words for them:

- **Vendor** (the operator): the party that builds and runs the application.
- **Tenant** (the customer): an organisation the application serves. Its
  people are **tenant users**.

"Operator" is acceptable as the *name of a vendor-side role* (a role claim, an
`ALLOWED_ROLES` value), not as the actor class. Do not write "application
provider", "end user", or "customer" for the classes themselves. Do not write
"SaaS" anywhere in a sample: not in prose, code comments, API model
documentation, package descriptions, or diagrams. The patterns apply to any
multi-tenant system, and the label narrows how readers place them.

## 1. Layout

Every sample lives in `samples/<name>/`, where `<name>` is kebab-case and
names the pattern, not the technology (`control-plane`, not `dynamodb-sfn`).

```
samples/<name>/
├── README.md                 # sections in §7 order
├── architecture.md           # the implemented state (§2.3)
├── adr/
│   ├── README.md             # index: number, title, status, date
│   └── NNNN-short-title.md   # one file per decision (§2.2)
├── threat-model.md           # threats and mitigations (§2.4)
├── design/
│   └── <name>.spec.md        # the specification the sample was built from (§2.1)
├── diagrams/
│   ├── <name>.drawio         # diagram source (§3)
│   └── <name>.drawio.svg     # exported, embedded in README
├── .projenrc.ts              # the only hand-edited project file (§4.1)
├── src/                      # CDK app (main.ts), the exported construct (§4.5), runtime code
├── test/                     # unit tests and integ.<flow>.ts (§5)
├── model/                    # Smithy model, only when the sample exposes an API
├── scripts/                  # provisioning or demo scripts, with CONVENTIONS.md
└── LICENSE                   # MIT-0
```

Files the sample generates or that are machine output are not committed:
projen-managed files other than `.projenrc.ts` are regenerated by `npx projen`;
Smithy output (`src/smithy/`), `cdk.out/`, and the integration test's
machine output (the integ-runner snapshot `test/*.snapshot/`, or the CDK CLI
driver's own cloud assembly) are gitignored; working notes (`TODO.md`) and agent
configuration (`.kiro/`) are gitignored.

### 1.1 Composition

Samples are building blocks. A sample consumes another sample instead of
re-implementing it, and publishes what it builds so a later sample can do the
same. The repository's shared concepts and the parameter namespace are in
[`ARCHITECTURE.md`](../ARCHITECTURE.md).

A sample's **published interface** is two things, both listed in its
specification's Contracts section (§2.1) and its README:

- **The construct** (§4.5): the build-time interface. Its props are the
  contract a consumer meets; its read-only properties are what it hands on.
- **Published parameters**: the deploy-time interface. The demo stack (never
  the construct, §4.5) writes the identifiers a consumer needs to SSM
  Parameter Store under the sample's namespace in `ARCHITECTURE.md` §5, and
  each parameter's name, value shape, and meaning are documented.

Consuming another sample follows these rules:

- **Depend on the interface, not the implementation.** A consumer reads the
  producer's published parameters or instantiates its exported construct.
  It never imports from another sample's `src/` by relative path, reads its
  stack outputs, or relies on resource names it does not publish.
- **The consumer's construct stays producer-agnostic.** It takes what it needs
  as props shaped by a contract (an issuer URL, a role ARN), so a reader can
  swap the producer for their own system. Only the demo app and the
  integration test name the producer.
- **Build-time reuse goes through the producer's package entry.** To
  instantiate another sample's construct, declare the producer as a local
  dependency (`file:../<producer>`) in `.projenrc.ts` and import from its
  `src/index.ts` exports. Record the first such dependency in an ADR.
- **Dependencies are declared and acyclic.** The consumer's README lists each
  producer, the topology or options it needs, and how to deploy it (§7). No
  sample depends, directly or transitively, on itself.
- **A published interface is a promise.** Renaming or reshaping a published
  parameter or a construct prop is a breaking change: record an ADR in the
  producer and update every consumer in the same pull request.
- **Integration tests compose; producers stay independent.** A consumer's
  integration test deploys its producers through their own documented deploy
  path, or reuses an existing deployment it detects, and tears down only what
  it deployed (§5.2). A producer's own integration test never needs a
  consumer.

## 2. Design trail

The design trail is written before the code and kept true after it. A reader
who only has the design trail should be able to predict the code; a reader who
only has the code should find every non-obvious choice explained.

### 2.1 Specification (`design/<name>.spec.md`)

The working specification the sample was built from. Sections, in order:

1. **Problem statement**: what the sample demonstrates, the deployment model
   it assumes (silo, pool, cell, bridge), and an explicit "what this is NOT"
   list that bounds the scope.
2. **Guiding principles**: numbered `P-n`, each a full sentence a later ADR
   can appeal to ("Correctness lives in conditional writes; reads only
   nominate"), with a paragraph on what the principle rules in and out.
3. **System shape**: required components, caller and identity model,
   deployment inputs.
4. **Data model**: every entity, its keys, its status values.
5. **API surface** (when there is an API): operations, status state machine,
   error shapes.
6. **Contracts**: what a deployer must supply, what the sample promises in
   return, the samples it consumes, and its published interface (§1.1).

The specification is not rewritten to match the implementation. When the
implementation diverges, record an ADR and, if the divergence changes a
promise, amend the specification with a dated note that points at the ADR.

### 2.2 Architecture decision records (`adr/`)

One file per decision, `adr/NNNN-short-kebab-title.md`, numbered with four
digits from `0001`, never reused; the next number is the current maximum plus
one. `adr/README.md` is the index, a table of number, title, status, and date,
updated in the same commit as the record it lists.

Each record uses this template:

```markdown
# ADR-NNNN: <Title in imperative form, e.g. "Use one shared CodeBuild project">

- Status: Proposed | Accepted | Deprecated | Superseded by ADR-NNNN
- Date: YYYY-MM-DD
- Deciders: FirstName LastName (Role), ...

## Context
The situation and the constraints that force a decision.

## Options considered
### Option 1: <name>
Pros / cons.
### Option 2: <name>
Pros / cons.

## Decision
Which option and the reasons that decided it. One paragraph.

## Consequences
What becomes easier, what becomes harder, follow-up work, and what would
trigger revisiting this decision.
```

Records are immutable once accepted. To change a decision, write a new record
that supersedes it and set the old one's status to `Superseded by ADR-NNNN`;
do not edit the old decision text. Write a record for choices a newcomer would
ask "why?" about: services, data model, identity, the asynchronous model, what
was deliberately left out, and every cdk-nag suppression that is not
self-evident. Decisions made during implementation get their own records, in
the same commit as the code that implements them. Cite records inline as
`(ADR-0013)` in the specification, `architecture.md`, the threat model, code
comments, and commit messages.

`samples/control-plane` predates this rule: its records were written in a
single file and later split, so its files use the original field layout
(bold `Status/Context/Decision/Consequences`) and are cited as `ADR-012`
rather than `ADR-0012`. New samples use the template above.

### 2.3 Architecture (`architecture.md`)

Describes the implemented state, not the plan. It opens with a status block:
implemented and verified or not, the date and Region of the last successful
integration test run, and what that run covered. Sections follow the
specification's shape (purpose, actors and identity, components, data model,
API, workflows) and cite records inline (`(ADR-0013)`) wherever a choice is
explained.

### 2.4 Threat model (`threat-model.md`)

Threats `T-n` and mitigations `M-n`. Every mitigation points at the ADR,
code location, or cdk-nag suppression that implements it; every threat without
a mitigation is listed as accepted with the reason. Findings from the security
review (§6) are dispositioned here. The sample README's security notes
reference this file by relative path; it lives inside the sample directory so
the link resolves for anyone who copies the sample out.

## 3. Architecture diagram

One high-level diagram per sample, embedded in the README's Architecture
section.

- **AWS Architecture Icons** (the current official set), with group frames for
  the AWS account and Region boundaries.
- **Left to right in the direction of traffic**: callers on the left, the
  sample's account in the middle, downstream targets (tenant deployments,
  external systems) on the right. Connected icons sit on a shared row or
  column so arrows are straight.
- **High level**: the components a reader needs to understand the pattern,
  not every resource. One diagram; put detail in `architecture.md`.
- **Source and export committed**: `diagrams/<name>.drawio` is the editable
  source; `diagrams/<name>.drawio.svg` is exported with the diagram XML
  embedded so GitHub renders it and draw.io reopens it. Both carry the MIT-0
  header as an XML comment after the declaration.
- **Legible when rendered**: no arrow crosses a caption, no caption overlaps
  another. Captions beside or above icons where an arrow passes below.
- **A one-sentence data path** directly under the embedded diagram, so the
  flow survives in raw Markdown, terminals, and screen readers.

Mermaid is acceptable for small sequence or state diagrams inside
`architecture.md`; the README architecture diagram is draw.io.

## 4. Code

### 4.1 Project

- projen `AwsCdkTypeScriptApp`, npm, `github: false`, `projenrcTs: true`,
  `license: 'MIT-0'` with the Amazon copyright owner. `.projenrc.ts` is the
  single hand-edited project file; run `npx projen` after changing it and
  commit the regenerated files.
- Dependencies pinned to exact versions. The integ-tests-alpha pin, when a
  sample uses it, matches the `aws-cdk-lib` version. Start a new sample from the newest sample's
  `.projenrc.ts` so the CDK version and pins stay aligned across the repo.
- Every authored file opens with the two-line header:

  ```
  // Copyright Amazon.com, Inc. or its affiliates. All Rights Reserved.
  // SPDX-License-Identifier: MIT-0
  ```

  Generated and third-party files never carry it.

### 4.2 API

When the sample exposes an API, model it in Smithy (`model/`), build the
server SDK as the `preCompile` task, and keep the generated output out of the
repository and out of lint. The model is the contract; the README API section
is derived from it.

Name resource lifecycle operations with the AWS verbs: `Create<Resource>`,
`Get<Resource>` (bound to the resource's `read` slot), `Update<Resource>`,
`Delete<Resource>`, `List<Resources>`, and `Put<Resource>` for
create-or-replace. Never `Read`, `Add`, `Remove`, `Fetch`, or `Describe`
(`GetTenant`, not `ReadTenant`; `CreateMembership`, not `AddMembership`).
Operations outside a lifecycle use a verb that says what they do
(`IssueToken`). Enforce this in `model/__global.smithy` with Smithy's
`StandardOperationVerb` validator at `DANGER` severity, so a bad name fails
`smithy build`. The validator ships in `software.amazon.smithy:smithy-linters`;
add it to the `maven.dependencies` in `smithy-build.json`, or Smithy only
warns that it cannot find the validator. List the lifecycle verbs plus any non-lifecycle verbs the
sample uses:

```smithy
metadata validators = [{
    name: "StandardOperationVerb"
    severity: "DANGER"
    configuration: {
        verbs: ["Create", "Get", "Update", "Delete", "List", "Put"]
        suggestAlternatives: {
            Read: ["Get"]
            Fetch: ["Get"]
            Describe: ["Get"]
            Add: ["Create"]
            Remove: ["Delete"]
        }
    }
}]
```

`samples/control-plane` predates this rule and does not carry the validator.

### 4.3 CDK

- Apply the cdk-nag `AwsSolutionsChecks` aspect in `src/main.ts`. Every
  suppression carries a reason that cites an ADR or a threat-model mitigation.
- Validate deployment context at synth and fail fast with a message that names
  the missing or malformed input. The build task supplies clearly labelled
  placeholder context so `npx projen build` synthesises without a deployment
  configuration; placeholders must be unusable in a real deployment.
- Removal policies are `DESTROY` and buckets auto-delete objects: a sample is
  torn down completely by `cdk destroy`.
- Least privilege is expressed as role asymmetry: a component that only needs
  to read gets a role that cannot write, and a role that runs caller-influenced
  work cannot reach the control data of other tenants.
- Encryption at rest and in transit on by default; logging with retention set.

### 4.4 Runtime

- No secrets, tokens, or caller payloads in logs. Scripts follow
  `scripts/CONVENTIONS.md` (no `set -x`, log names and status, never values).
- Synthetic data only: invented tenants, documents, identifiers, and account
  IDs in fixtures, tests, and documentation. Grep the tree for the deployment
  account ID before every commit.
- Idempotency and retry safety where retries actually happen; document the
  benign races you tolerate and the corruption you prevent.

### 4.5 Deliverable: a CDK construct

The pattern ships as a reusable CDK construct, not only as a stack. A reader
takes the pattern into their own system by instantiating the construct in
their own app, so the construct is the unit of reuse and the stack in
`src/main.ts` is a thin demo that wires it to the sample's dependencies.

- Export the construct (and its props interface) from `src/index.ts`. One
  construct per pattern; name it after the pattern
  (`IsolatedRuntime`, not `AgentCoreStack`).
- The construct takes its dependencies as props (an issuer, a table, a key)
  and creates none of them. What the deployer must supply is the
  specification's Contracts section (§2.1), expressed as the props type.
- Options the pattern offers are typed props with secure defaults; an
  optional behaviour is off unless set. Validate props in the constructor and
  fail at synth with a message that names the prop.
- The construct applies no cdk-nag aspect and no `App`-level settings; it
  carries its own `NagSuppressions` with reasons, so a consumer who applies
  cdk-nag sees the same result as the sample.
- Expose what a consumer needs to wire the next component (endpoint URL, role,
  ARNs) as read-only properties, not as stack outputs or SSM parameters the
  construct writes for itself. The demo stack publishes those properties as
  the sample's published parameters (§1.1).
- Unit tests synthesise the construct inside a bare test stack, once per
  option combination the specification promises.

`samples/control-plane` and `samples/tenant-identity` predate this rule and
ship stacks.

## 5. Tests

### 5.1 Unit tests

Alongside the code in `test/`. Cover runtime logic with mocked AWS clients
(`aws-sdk-client-mock`) and the synthesised template with assertions for the
things the threat model relies on: roles and their policies, encryption,
removal policies, cdk-nag suppressions.

### 5.2 Integration test

One `test/integ.<flow>.ts` app, run through a projen task named `integ`,
with one of two drivers:

- **`@aws-cdk/integ-runner`** (the default). Always `--force` and
  `--update-on-failed`; the snapshot is gitignored, so no workflow depends on
  a committed snapshot. Assertions run as integ-tests-alpha `awsApiCall`s or
  as a `postDeploy` hook.
- **The CDK CLI in `scripts/integ.sh`**, when the test deploys several
  independent stacks. integ-runner deploys and destroys a test's stacks one
  at a time, so a multi-stack test spends most of its run waiting. The
  script synthesises the app into its own gitignored cloud assembly, runs
  `cdk deploy --all --concurrency <n>`, runs the assertions (typically the
  e2e suite), and runs `cdk destroy --all --force --concurrency <n>` from an
  exit trap, so the destroy also runs when the deploy or the assertions
  fail. It exits non-zero if any step failed. Record the choice in an ADR
  (tenant-identity ADR-0023 is the worked example).

Either way, the test:

- Runs in **exactly one Region**, selected by `AWS_REGION`; the task fails
  fast when it is unset so no multi-Region default ever applies.
- Stands up its own dependencies (a bucket of sample scripts, the samples it
  consumes) rather than assuming anything exists in the account. A consumed
  sample is deployed through its own documented deploy path, or an existing
  deployment is detected and reused; the test tears down only what it
  deployed (§1.1).
- Drives the **full lifecycle**: every API operation or every step of the
  demonstrated flow, including the failure paths the specification models,
  and teardown. The test passing means the sample can be created, used, and
  destroyed without leaving resources behind.
- The README states the runtime and approximate cost of one run.

Record the date, Region, and coverage of the last green run in the
`architecture.md` status block.

## 6. Security review

Before the pull request, on the synthesised tree:

1. `npx projen build` under the deployment profile, so `cdk.out/` carries the
   account and Region the sample is deployed to rather than the workstation's.
2. Run the static scanners the team uses (currently ProtoShield and the
   Automated Security Helper) against the sample directory with `cdk.out/`
   present.
3. Disposition every finding in `threat-model.md` or a new ADR: fixed, accepted
   with reason, or false positive with the evidence. Fix findings that are
   cheap and legitimate rather than documenting around them.
4. Scanner outputs stay out of the repository; the pull request description
   summarises the results.

Secret scanners read git history. A secret-looking string in a removed file
still fires on the old commit; accept such false positives through the
scanner's ignore mechanism, never by rewriting history.

## 7. Sample README

Sections, in this order, omitting only those that do not apply:

1. **Title and summary**: the pattern in one paragraph, and what the sample
   is NOT.
2. **Architecture**: the embedded diagram (§3), its one-sentence data path,
   and a short component list.
3. **How it works**: the primary flow, step by step, with pointers into
   `architecture.md` for depth.
4. **Deploy**: prerequisites, including each consumed sample with the
   topology or options it needs and how to deploy it (§1.1), the exact `npx projen build` and
   `npx cdk deploy` commands with every `--context` input explained,
   teardown, and a short snippet that instantiates the construct in a
   consumer's own app (§4.5).
5. **Deployment integration test**: how to run `npx projen integ`, what it
   stands up, runtime, cost, and the single-Region rule.
6. **End-to-end demo**: a runnable `scripts/demo.sh` that walks the flow
   against a deployed stack, checks each response, and cleans up what it
   created on exit (also on failure). The README section gives the command
   and a step table (call and expected result), not the commands themselves.
7. **API** (when there is one): operations and status machine, derived from
   the Smithy model.
8. **Security notes**: the identity model, the trust boundaries, and a link
   to `threat-model.md`.
9. **Production hardening checklist**: what a reader must add before using
   the pattern in production, each item tied to a threat-model mitigation.
10. **Design trail**: links to `design/<name>.spec.md`, `adr/`, and
    `architecture.md`.

## 8. Root README

Adding a sample changes three places in the repository `README.md`:

1. A row in the **Samples** table: linked name and a one-sentence
   description.
2. A `## <Sample name>` section of two or three paragraphs: the problem, the
   shape of the solution, and a link to the sample directory.
3. The matching entry under **Contents**.

It also changes [`ARCHITECTURE.md`](../ARCHITECTURE.md): the sample's place in
the concept map (§6 there), its parameter namespace (§5 there), and the
samples it consumes.

## 9. Definition of done

A sample is ready to merge when every line is true:

- [ ] Layout matches §1; nothing generated or machine-produced is committed.
- [ ] Composition per §1.1: consumed samples are used only through their
      published interface and listed in the README; this sample's published
      interface (construct and parameters) is documented in the specification
      and README, and its parameters sit in its `ARCHITECTURE.md` namespace.
- [ ] Specification written before the code, with numbered principles and an
      explicit scope boundary; divergences recorded as ADRs.
- [ ] One file per ADR in `adr/` with the index current; options considered named,
      implementation-time decisions included.
- [ ] `architecture.md` describes the implemented state and carries a dated
      verification status.
- [ ] `threat-model.md` present; every mitigation points at code, an ADR, or a
      suppression; scan findings dispositioned.
- [ ] Diagram follows §3: AWS icons, left to right, high level, draw.io
      source and embedded SVG committed, one-sentence data path, no text
      overlaps.
- [ ] projen project per §4.1; dependencies pinned; MIT-0 header on every
      authored file and on no generated file.
- [ ] The pattern is a construct exported from `src/index.ts` with typed,
      validated props and secure defaults (§4.5); the stack is a thin demo.
- [ ] cdk-nag aspect applied; every suppression cites an ADR or mitigation.
- [ ] Fail-fast context validation; build placeholders cannot reach a real
      deployment.
- [ ] `DESTROY` removal policies; teardown verified to leave nothing behind.
- [ ] Synthetic data only; no deployment account ID in the tree.
- [ ] Terminology per the introduction: actors are vendor and tenant;
      `git grep -i -E 'saas|application provider|end[- ]user' samples/<name>`
      returns nothing.
- [ ] Unit tests green; `npx projen build` clean.
- [ ] Integration test green in one Region (integ-runner with `--force`, or
      the CDK CLI driver); date, Region, and coverage recorded in
      `architecture.md`.
- [ ] Security review run on the synthesised tree; results summarised in the
      pull request.
- [ ] Sample README has every applicable §7 section in order.
- [ ] Root README table row, section, and Contents entry added;
      `ARCHITECTURE.md` concept map and parameter namespace updated.
