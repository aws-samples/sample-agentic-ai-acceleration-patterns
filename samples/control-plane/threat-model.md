# Control Plane — Threat Model

> Threat (`T`) and mitigation (`M`) identifiers are stable keys cited by the
> README, the ADRs, code comments, and tests. Only cited identifiers are
> listed; the gaps in the numbering are deliberate and are never reused.

Scope: the control plane's API edge, its identity model, the
provisioning path into CodeBuild and from there into each registered
account, the vendor hook path inside the control plane account (spec
§6.5, ADR-044, specified and not yet built), and the operational data it
emits. The application plane an application's definition provisions is
out of scope here, except where the control plane's choices bound its
blast radius. Two trust populations matter: the vendor, who runs the
control plane and owns the fleet accounts, and customers, who own
tenant-owned accounts and install the provisioning role pair there (spec
§6.4).

## Threats

| ID | Threat | Consequence | Status | Mitigations |
|---|---|---|---|---|
| T1 | Stolen operator token | Full admin over the tenant fleet for the token's remaining lifetime plus the authorizer cache window | Mitigated in code; residual bounded by the issuer's token lifetime (operational) | M9, M11, M13, M17, M26 |
| T2 | Issuer misconfiguration: `vendorIdpIssuerUrl` / `vendorIdpAudience` point at a general workforce or customer issuer | Every member of that population is a control-plane admin; with `readerRoles` set, a generic reader value (`reader`, `viewer`) in that population reads the whole fleet (T36) | Mitigated in code (fail-closed role gate) and operationally (dedicated issuer) | M9, M13 |
| T5 | Poisoned provisioning source: a malicious commit on the ref an application's cells build from, or on the ref a global or application hook builds from | Arbitrary code execution across that application's cells, in every account that hosts them, under the provisioning roles on the next lifecycle operation. A poisoned hook source runs in the control plane account under its hook role on every event it names, for every application when it is a global hook (T41). Deleting or replacing a poisoned global hook stops it only for operations accepted afterwards: every execution already accepted keeps running it until it ends, up to the execution timeout, and `StopExecution`, the only stop, strands that execution's record (spec §7.2). **Highest-consequence item.** | Partially mitigated: the sample can express an immutable pin but `PutApplication` and `PutHook` warn rather than refuse an unpinned ref; hook roles hold only deployer-attached policies and never the pair (M30); the rest is operational | M10, M30 |
| T9 | Destructive API operations not attributable to an operator | No audit trail from an access-log line to a person | Mitigated in code | M12 |
| T10 | Application-plane changes made by provisioning scripts attributed only to the shared fleet CodeBuild roles | No link from an application-plane change back to the initiating API call | Mitigated in code | M12 |
| T13 | Log exposure: build logs readable by anyone with log-group access, scripts echoing fetched values, service-created log groups that never expire | Build logs become an unintended secrets store with unbounded retention | Mitigated in code and by script conventions | M15 |
| T16 | Cost and concurrency amplification: each `CreateDeployment` can create a cell and run up to two hour-long builds, plus one hook build for every hook its events resolve (up to twenty, spec R-39) | A leaked token or runaway client drives CodeBuild cost and exhausts concurrency | Mitigated in code (caps, throttling, alarms); tighter per-method limits are operational | M11, M17 |
| T20 | Issuer scope creep: gradual client or audience reuse on the dedicated issuer, or a listed machine client reused by another system (`clientIds`, T37) | Silent widening of the admin population without any configuration change on the control plane; with `readerRoles` set, a generic reader value (`reader`, `viewer`) in that population reads the whole fleet (T36) | Mitigated in code (role gate) and operationally (client review) | M9, M13, M27 |
| T21 | Over-broad deployer-supplied policy on the tenant provisioning role: `tenantBuildManagedPolicyArns` attaches a managed policy wider than the tenant scripts need | That account's tenant provisioning role, which runs every tenant script in the account, gains that reach, so a compromised source or a bad script acts with it across the account's cells | Mitigated in code (synth-time ARN validation, same-account only) and by owner responsibility (attach only least-privilege policies the producer publishes); the owner of each account attaches their own (ADR-025) | M18, M22 |
| T22 | Confused deputy against a customer account: a third party learns a customer's provisioning role ARN and has the control plane act there (by registering the account, or because the customer's trust policy admits the control plane account alone) | The control plane provisions, updates, or deletes resources in a customer's account on behalf of someone who is not that customer | Mitigated in code: the trust policy pins `aws:PrincipalArn` to the control plane's three roles, so no other account can assume the pair; `PutAccount` refuses a tenant-owned account without an external id (ADR-029) and refuses any account whose pair admits the call without the supplied id (ADR-030), so registration needs a value only the owner handed out and the pair is proven to enforce it. The external id gates registration only: any operator uses the stored value afterwards (T27) | M19, M20, M13 |
| T23 | Wildcard-account AssumeRole: the build roles (and the API function's probe) may assume `<fleet>-cell-provisioning` / `<fleet>-tenant-provisioning` in *any* account, because accounts are registered at run time | A mistyped or malicious `PutAccount` can point the fleet at an account the vendor did not intend — but only one whose owner already installed a role with that name trusting this control plane | Mitigated in code (fixed role names, handshake probe, explicit registration); the target trust policy is the gate; an organisation-scoped condition (`aws:ResourceOrgID`) on the build roles is operational for vendor-only fleets | M20, M19 |
| T24 | Assumed-role credential exposure in builds: the buildspec exports the provisioning role's credentials to the script as environment variables; `set -x`, `env`, or an echo lands them in the build log | One-hour credentials for a customer's account in a log group readable by anyone with log access | Mitigated in code (credentials fetched into shell variables inside the buildspec, never into CodeBuild environment variables or execution input; role chaining caps them at one hour) and by script conventions; log retention bounds the window | M21, M15 |
| T25 | Over-privileged provisioning role pair in an account: an owner installs the pair and then widens it (inline edits, extra policies) beyond spec §6.2 | A poisoned source (T5) or a bad script acts with that reach in that account; for a customer account, that is the customer's own blast radius | Mitigated by the shipped least-privilege pair and the cell/tenant asymmetry; widening is the owner's deliberate act and stays theirs | M22, M10 |
| T26 | Revoked or broken pair under live cells: the owner deletes or changes the role pair while cells exist in the account | Builds there fail into `*_FAILED`; cleanup needs the pair back, so cell and account records in that account cannot be deleted through the API until the owner restores it | Accepted: revocation is the owner's right and the control plane must not hold a way around it; the records stay consistent and the remediation (restore the pair, then delete; or manual record repair) is documented | M23 (detective only) |
| T27 | Cross-customer placement: an operator names customer B's tenant-owned account in a `CreateDeployment` for the tenant that is customer A, by mistake or intent | Customer B's account hosts a stranger's deployment; B's data is not exposed, but B pays for and is responsible for the resources | Not mitigated in code: operators are fully privileged (ADR-015/018). The control plane knows the customer — a tenant, whose deployments belong to it (ADR-037) — but a tenant-owned account records only `owner: TENANT`, not which tenant it belongs to, so nothing ties A's deployments to A's account. `applicationIds` narrows which applications an account admits (ADR-033), not which tenants. Accepted at sample scope; finer operator roles with account scoping are the recorded seam (spec §11). Detective: the operator id in the account's CloudTrail, and `ListDeployments?tenantId=` with `GetCell` showing where each of a tenant's deployments lives | M23, M12 |
| T28 | External id leakage: the value rides the resolved execution input (as a plaintext CodeBuild environment-variable override, readable by anyone with `codebuild:BatchGetBuilds` or Step Functions history access) to reach the AssumeRole call | A leaked external id removes the T22 guard for that account until the owner rotates it | Mitigated in code (never returned by the API, never logged by the sample; the readers above are the operator role and the account's own administrators) and operationally (rotate by redeploying the pair and re-running `PutAccount`) | M19 |
| T29 | Provisioning script reaches the build role: the script runs in the same container as the agent that assumed the pair, and the CodeBuild container credential endpoint (`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`) hands out the BUILD role's credentials to any process that asks; with them the script can assume the pair in every registered account, not just the one it was placed in | A tenant-controlled script in one account provisions, reads or deletes in every other account of the fleet | Mitigated in code: the buildspec removes the container credential variables and the external id from the script's environment before it runs, and fails closed when AssumeRole returns no credentials. Residual: the agent process still holds both, so an attacker with a container escape or `/proc` access to the agent is not stopped; that is the CodeBuild trust boundary (T13) | M24, M22 |
| T30 | API role reach: the `<fleet>-api` role may assume both halves of the pair in every registered account (for the registration probe, ADR-028), so a compromise of the API function — a dependency with a payload, an injection through a request field — reaches every account's SSM namespaces, not just the control plane's table. The API role also holds `states:StartExecution` on the workflow, which runs whatever hook source and scripts the execution input names, so the same compromise runs any code as `<fleet>-global-hook` and `<fleet>-app-hook` and as the provisioning build roles (spec R-41) | Full provisioning rights in every registered account from one Lambda, and every hook role's reach in the control plane account | Partially mitigated in code: the probe passes a deny-all session policy on every AssumeRole, so the credentials it receives can do nothing even if captured (`src/tenant/account.handshake.ts`, `PROBE_SESSION_POLICY`; `test/tenant/account.handshake.test.ts`), and the API role's grant is bounded to the two role names (M20). Residual: code running as the API role could call AssumeRole itself without the session policy; the grant exists. Hardening: an `aws:ResourceOrgID` condition on the API role's grant for vendor-only fleets, and the API function's dependency pinning (M10). Specified, not built: the API role is the only principal granted `states:StartExecution` on the workflow, and no build or hook role holds it (spec R-41, a §10 unit assertion) | M20, M13, M30 |
| T31 | Name collision: the pair's role names and the pair stack's name derive from `fleetName` alone. An account that already has a role or stack of that name (another vendor's fleet with the same default, a customer's own `control-plane-*` roles) fails the install, or — if the names belong to another control plane's pair — is registered against a trust policy written for someone else | Install failure at best; at worst an account registered by vendor A whose pair trusts vendor B (B's roles are named, so A's probe is refused — the handshake catches it) | Mitigated by the handshake (M20: a pair trusting another control plane refuses A's probe) and by the stack name carrying the fleet name. Residual: pick a fleet name the vendor owns, not the default, for any fleet that leaves the vendor's accounts; recorded in the README hardening checklist | M20 |
| T32 | Trust outliving the control plane: a customer's pair trusts `<control plane account>` narrowed to three role names. If the vendor deletes the control plane and the account is later reused or the role names recreated for something else, the customer's pair still trusts them | Whatever next holds those role ARNs in that account can act in the customer's account | Not mitigated in code: the control plane cannot reach into a customer's trust policy, and must not (T26). Accepted at sample scope; the README tells the customer that `DeleteAccount` deregisters the account on the vendor's side only and that removing the pair is their act | — |
| T33 | Customer runs the vendor's CDK app: installing the pair means synthesising the sample's `CellAccountStack` from the vendor's repository with the customer's credentials, so the customer executes vendor-supplied code with administrative rights in their account | Supply chain: a malicious or compromised revision of the app does anything in the customer's account at install time | Not mitigated in code. Accepted at sample scope, with the mitigation in the customer's hands: review the synthesised template (two roles, two policies, and one optional demo parameter per `demoApplicationIds` entry) before deploy, or install the pair from the template directly instead of the CDK app; `cdk synth --context cellAccount=...` produces it | — |
| T34 | Operator-registered code: an operator (or a stolen operator token, T1) calls `PutApplication` with a source the attacker controls and `CreateDeployment` to run it, so the provisioning pair in every account that admits the application — a customer's tenant-owned account included — executes attacker code on the next build. An application's definition is API data, not a deployment input (ADR-032), so this needs no deployer credentials and no redeploy. The same token can name hook code it controls, through `PutHook` or an application's `hooks` (ADR-044), which then runs in the control plane account under a hook role on every matching event, every application's for a global hook, or register a global pre hook that refuses every create (T43) | Arbitrary code under the provisioning roles of every admitting account, from one operator token; hook code under the hook roles in the control plane account | Partially mitigated in code: the pin warning at `PutApplication` and `PutHook` (M10), hook roles that hold only what the deployer attached (M30) and the operator id on every build and AssumeRole (M12, M23) make the act attributable, `applicationIds` on a customer's account limits which applications may build there (ADR-033), and the role pair bounds what the code can do (M22). Not mitigated: nothing distinguishes an operator who may register applications from one who may onboard tenants (ADR-015/018); finer operator roles are the recorded seam (spec §11). Operational: alert on `PutApplication` and `PutHook`, treat a definition or hook change as a release, pin sources to a commit SHA | M10, M12, M22, M23, M13, M30 |
| T35 | Parameter value exposure: deployment and cell parameter values (ADR-039, ADR-040) are plain text on the deployment or cell record, returned by `GetDeployment` and `GetCell`, carried in the Step Functions execution input and its history, and passed as CodeBuild environment-variable overrides, readable through `codebuild:BatchGetBuilds`; an operator who puts a secret there, or a script that echoes one, exposes it | Anyone who can read the table, the execution history or `BatchGetBuilds` in the control plane account (the operator role, every reader (R-36), the account's administrators) reads every value; a value echoed by a script lands in the build log (T13) | Mitigated by contract and in code: values must not be secrets (spec N-11), a secret is passed by name and read by the script under its own role; the service logs parameter names, never values, and its error messages name the parameter, not the value; values are capped at 1,024 bytes with no control characters and only declared names are accepted. Residual: nothing can tell a secret from any other string, so the rule is the operator's to keep. API Gateway's request validation runs before the service, and its execution log (INFO level) can record a value it refused for breaking the model, for example one over the length limit; that log is in the control plane account, readable by the same principals | M25, M15 |
| T36 | Stolen reader token, or a reader grant on the wrong population: a token with a `readerRoles` value (R-36) | Disclosure, no change to the fleet: tenant names, account ids (customer accounts included), cell placement, build ids, parameter values (T35), and the source location and version of every application and every hook, which name the repositories to compromise for T34 | Mitigated in code (spec R-36, R-37; ADR-042): the reader grant is the `GET` operations only, in the authorizer policy and again in the service, failing closed on a missing grant; `readerRoles` is empty by default, a value in both role lists fails synth and cold start. Operational: a namespaced reader value. Residual: the disclosure itself, bounded by the issuer's token lifetime | M26, M9, M13 |
| T37 | Audience bypass: a token without `aud`, minted on the vendor IdP for a client the control plane was never meant to trust, a person's access token issued through a listed client, or a listed client's token minted for another API on the same issuer and replayed here | That population gets whatever grant its `role` maps to, with no audience to stop it | Mitigated in code (spec R-38; ADR-043): the no-`aud` path admits only a `client_id` in `clientIds` (empty by default) that also equals `sub`, so only a listed client acting as itself, and, when `requiredScope` is set, only a token whose `scope` holds this API's scope; any `aud` key, even `[]`, `""` or `null`, takes the audience path and never falls back; `role` is still required and still picks the grant. Operational: list only the vendor's own machine clients and set `requiredScope` when a listed client calls another API on the issuer (M9) | M27, M9, M13 |
| T38 | Stolen machine client secret: the secret of a client in `clientIds` | Fresh tokens on demand with that client's grant, the operator grant included, until the secret is rotated or the client deleted; no second factor, so the token-lifetime residual of T1 and T36 does not bound it | Operational (M9): secret in a secrets store, rotation, the reader role unless the client must operate, revocation by deleting the client. In code: the access log names the client as `operatorId` (M12), so its calls are attributable | M9, M12 |
| T39 | Tenant acts as the vendor's script: a tenant-owned account controls its provisioning role pair, so any downstream system a cell or tenant script calls with the pair (a route registrar, a metering or inventory API) can be called by the tenant at any time, with any body. For the `tenant-front-door` registrar that means writing, deleting and re-creating its own route, and lifting a suspension by re-creating the entry | A downstream system's vendor-side state for that tenant is whatever the tenant says | Specified, not built (ADR-044, Proposed): vendor hooks run in the control plane account under hook roles that no cell account holds or trusts, and only a control plane operation starts one, so a system that admits only a hook role admits only the vendor. Not mitigated for a system a script still calls with the pair; that system must treat every call from a tenant-owned account as the tenant's | M28, M24 |
| T40 | Untrusted script outputs: a post hook acts on `SCRIPT_OUTPUTS` (spec R-43), which in a tenant-owned account reflect what the tenant controls (SSM values, resource names, endpoints it can change); a hook that takes an identity or a target from them can be steered to act on another tenant's or another cell's state | A hook writes, on the tenant's say-so, state that belongs to someone else, with the hook role's reach | Specified, not built: the provisioning buildspec checks outputs for shape and size (a JSON object of string values, printable ASCII only (0x20 to 0x7E), at most 4,096 bytes in compact form), a format check rather than a trust boundary because it runs in the container the script ran in (M29); the workflow checks the value again in the script task's `Output` (M32); outputs are never read or stored by the control plane, and dropped when invalid on delete; hooks take every identity from the control plane's own variables and validate every value they use (spec R-42, R-43). Residual: a hook that uses a value unchecked; that check is the hook author's | M29, M32 |
| T41 | Hook role reach: the hook roles run arbitrary vendor code in the control plane account with whatever the deployer attaches. An application hook could reach what only a global hook should; one application's hooks can use what another's need, because every application hook runs as `<fleet>-app-hook`; every global hook runs as `<fleet>-global-hook`, so a metering or audit global hook can write what the route registrar writes; a hook project accepts source and buildspec overrides, so any principal with `codebuild:StartBuild` on it runs any code as its role, and so does any principal with `states:StartExecution` on the workflow, which starts whatever hook source its input names; the API role holds that grant (T30); an attached policy that grants a hook role `states:StartExecution` on the workflow, `codebuild:StartBuild` on a provisioning project or a write to the table (whose `PK=HOOK` partition declares hooks) would hand it the provisioning build roles and with them every registered account's pair; any other policy over the control plane's own resources gives every hook of that scope that reach over the control plane | A compromised or buggy hook acts with that reach from the vendor's most sensitive account | Specified, not built: one project and one role per scope, no role override, nothing granted beyond logs and source by the stack, deployer policies validated as in M18, and an ARN in both lists fails synth (spec R-41, §3.3); only the workflow role may start a hook build and it holds no `iam:PassRole` on either hook role, while the provisioning build roles and the API role hold neither, and only the API role holds `states:StartExecution` on the workflow (spec R-41, §10 unit assertions); each build role, each hook role and the two pair roles of the stack's own account carry an inline explicit deny on `states:StartExecution` on the workflow, starting builds in all four projects and writes to the table, which holds whatever a deployer attaches and also closes the older `tenantBuildManagedPolicyArns` path (spec R-41, §10 unit assertion). Accepted: one shared role per scope; a role per application or per global hook is the seam (spec §11). Operational: the deny covers only those roles, so grant `codebuild:StartBuild` on any of the four projects, or `states:StartExecution` on the workflow, to no other principal in the control plane account; a principal the deployer grants either holds the roles the project or the workflow runs as. Operational: attach least-privilege policies, never one over the control plane's own resources | M30, M18 |
| T42 | Stale external state after a skipped delete hook: a delete hook that keeps failing, by bug or by congestion (every hook build of a scope goes through one project capped at five, and a refused start is retried for 5 minutes per attempt until the hook's budget is spent), is skipped so cleanup stays reachable (P-9), so a route, a meter or an inventory entry can outlive the cell or deployment it names | A route that points at a deleted cell's origin; a meter still counting a removed deployment | Accepted by design, with detection: the skip is logged with scope, hook id, event, record and whether the budget ran out, and counted in an alarmed metric (spec R-46); pre delete hooks run before the delete script, so a hook that succeeds removes external state before the resources go. Reconciling a skip is the external system's job | M31 |
| T43 | Hook as a fleet-wide stop: a failing or slow global pre hook, by bug or through a stolen operator token (T34), fails every create and update of every application; each hook attempt can take up to 47 minutes, queue included. Congestion alone fails them too: every global hook build of the fleet goes through one project capped at five concurrent builds, a sixth start is refused (spec §9.1, H-9) and retried every 30 seconds for 5 minutes, and then the create or update fails as "cannot start" | Onboarding and updates stop fleet-wide until an operator fixes or deletes the hook; executions run longer and cost more (T16) | Partially mitigated (specified, not built): deletes are never gated (spec R-46), so cleanup stays reachable; run timeouts are 5 to 30 minutes, refused starts get at most 5 minutes and the queued timeout is 10 minutes less the minutes refused, so both together take at most 10, and each scope holds at most five hooks (R-39, R-46); `DeleteHook` removes a gate for every operation accepted afterwards (R-40), while executions already accepted keep running it until they end or `StopExecution` strands them (spec §7.2); `statusReason` names the hook that failed and tells a queued timeout from a run timeout and from a start refused by congestion. Operational: alert on `PutHook` and on a rise in `*_FAILED` | M17, M12, M31 |
| T44 | Tenant-forced failure through script outputs: in a tenant-owned account the outputs follow what the tenant controls. A value past CodeBuild's exported-variable limit comes back empty while the build reports `SUCCEEDED` (spec §9.1, H-1); a value that bypasses the container check and is large pushes a state past 256 KiB, whose `States.DataLimitExceeded` no Catch sees, so no `*_FAILED` write runs; a hook buildspec that interpolated `SCRIPT_OUTPUTS`, `TENANT_NAME` or a `PARAM_` value into a command would run tenant text as code | The tenant strands its own deployment's record in `CREATING` or `UPDATING` on demand, or runs code with a hook role's reach in the control plane account | Specified, not built: the script task's `Output` rejects an empty, over-long or malformed value, taking the failure path on create and update and `{}` on delete (M32); the buildspec exports `SCRIPT_OUTPUTS` alone and always sets it (M29); the hook buildspec passes every value as an environment variable only and runs `bash "$HOOK_SCRIPT"` (spec R-41, M29). Residual: the guard admits at most 4,096 printable ASCII characters, at most 8 KiB in state once escaped, which the payload budget counts (spec §8.1); its pattern is linear, so a near miss cannot stall it (spec R-43) | M32, M29 |

## Mitigations

Each mitigation names where it lives. "Operational" items are the deployer's
responsibility and appear in the README's production hardening checklist.

| ID | Mitigation | Where | Threats |
|---|---|---|---|
| M9 | Identity hardening: dedicated control-plane issuer, deployment-time verification of issuer and audience, short-lived tokens, MFA for operators, machine client secrets in a secrets store, rotated, revoked by deleting the client, and given the reader role unless they must operate, `requiredScope` set when a listed client calls another API on the issuer, periodic review of client registrations and of `clientIds` beside them | Operational: README "Production hardening checklist", Identity (M9) | T1, T2, T20, T36, T37, T38 |
| M10 | Supply-chain pinning: an application's `SourceDefinition.sourceVersion` pins its provisioning source to a full 40-character commit SHA, stamped onto each of its cells and into every build as the CodeBuild `SourceVersion` override; `PutApplication` logs a warning naming the application when the ref is absent or mutable, and accepts the definition. Every hook's `source` follows the same rule and pass-through: `PutApplication` warns for each application hook and `PutHook` for a global hook, naming the hook (spec R-39, ADR-044; not built). Branch protection, signed commits, read-only deploy credentials, and treating a definition-replacing `PutApplication` or a `PutHook` as a release are operational | [ADR-020](./adr/0020-supply-chain-pinning-warn-and-allow.md), [ADR-032](./adr/0032-register-applications-at-run-time-and-stamp-their-definition-onto-cells.md); `src/shared/service-config.ts` (`sourcePinningWarning`), `src/tenant/tenant.ts` (`PutApplication`), `src/tenant/tenant.sfn.ts`; `test/main.test.ts` (pin check, SourceVersion pass-through), `test/tenant/tenant.test.ts` (warning at `PutApplication`); README, Supply-chain hardening (M10) | T5 |
| M11 | Edge protection: stage-wide throttling (20 rps rate, 40 burst) in the sample; AWS WAF web ACL, per-method usage plans, and a source-IP resource policy are operational | `src/tenant/tenant.cdk.ts` (stage throttling); README, Edge protection (M11); cdk-nag suppression on WAF association with reason | T1, T16 |
| M12 | Operator identity end-to-end: the verified JWT `sub` is the authorizer principal, appears in API Gateway access logs, rides the Step Functions execution input, and reaches every build as `OPERATOR_ID`, hook builds included (spec R-42, not built) | [ADR-019](./adr/0019-operator-identity-end-to-end.md); `src/tenant/tenant.cdk.ts` (access-log format), `src/tenant/tenant.ts`, `src/tenant/tenant.sfn.ts`; `test/main.test.ts` (access logging, OPERATOR_ID override) | T9, T10, T38, T43 |
| M13 | Role-claim enforcement: the authorizer requires the `role` claim to be in one of two deployment-configured lists (`ALLOWED_ROLES`, default `operator`; `READER_ROLES`, default none, M26) and fails closed; authentication alone is not sufficient | [ADR-018](./adr/0018-enforce-role-claim.md) (amends [ADR-015](./adr/0015-authentication-only-gating.md)); `src/shared/authorizer.function.ts`, `src/shared/authorizer-policy.ts`, `src/tenant/tenant.cdk.ts`; `test/main.test.ts` (role list wiring), `test/shared/authorizer.test.ts` | T1, T2, T20, T36, T37 |
| M15 | Bounded log exposure: explicit log groups with one-month retention for the Lambda functions and every CodeBuild project: the two provisioning projects and the two hook projects (spec R-41, not built); provisioning scripts never use `set -x` and log names and status, not values | [ADR-021](./adr/0021-bounded-blast-radius.md); `src/tenant/tenant.cdk.ts`, `src/tenant/tenant.sfn.ts`; `scripts/CONVENTIONS.md`; `test/main.test.ts` (every log group has bounded retention) | T13 |

## Open items

- **T5 remains the highest-consequence open item.** `PutApplication` warns
  on an unpinned or mutable source ref instead of refusing it, so an
  operator can still run an application's cells from a branch. ADR-020
  records why (an unpinned demo must keep working). A deployment that
  refuses mutable refs turns the `sourcePinningWarning` result in
  `PutApplication` (`src/tenant/tenant.ts`) into a `ValidationException`.
- Alarms have no actions. Wiring them to a notification target is the
  deployer's choice of channel.
- **T27 (cross-customer placement) is accepted, not mitigated.** Any
  operator may target any registered account. A control plane serving
  several customers' accounts needs finer operator roles
  (spec §11) with account scoping before a broader operator
  population connects. The sample's trust model (one fully privileged
  operator population, ADR-015) is where this is stated.
- **T26 (revoked pair under live cells) is accepted by design.** The owner's
  ability to cut access must not have a control-plane bypass. The cost is
  that cleanup of that account's records needs the pair restored first, or
  manual repair; the README's remediation section states both.
- **Vendor hooks (ADR-044) are specified, not built.** T39 stays open for
  the `tenant-front-door` registrar until its route writes move from the
  scripts to hooks and it stops admitting the provisioning roles. T40 to
  T44 and M28 to M32 describe the specified design; their code pointers
  are added when it is built.
- The handshake probe (M20) is point-in-time. A periodic read-only re-probe
  of registered accounts would turn a silent revocation into a signal
  before the next build fails; noted, not built.
