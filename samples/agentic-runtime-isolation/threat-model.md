# Agentic Runtime Isolation: Threat Model

> Status: **Implemented (v2).** 102 current threats and 80 current mitigations
> (ids T-1 to T-105 and M-1 to M-83; T-14, T-15, T-41, M-8, M-9 and M-31 are
> [retired with v1](#retired-v1)). Last review 2026-11-06. Last green integration
> run: run 15, 2026-11-06, eu-central-1, 58/58 steps, commit `3b2d727` on PR 21.
> History is in the [ADRs](./adr/) and the git log.

Scope: the `SharedIngress` and `AgentBackend` constructs (one ingress, one
or more AgentCore Runtimes, a backend registry in SSM Parameter Store;
ADR-0024), with either ingress (API Gateway REST with Lambda, or AgentCore
Gateway with a REQUEST interceptor), the always-on token vending machine and
the optional modules (session mapping, the `requiredScopes` floor), the
demo stack, and the published
and consumed SSM parameters. (v2) Also the entitlement store and its API,
the token signer with its JWKS and discovery routes, the transaction token,
the tools gateways (Policy, interceptor, the optional list filter, rate
limits; one or more, ADR-0041), the signed tenant
context, `ToolTarget` and the tool-side library and TVM. Out of scope: how
the identity provider issues
and narrows tokens ([tenant-identity's threat model](../tenant-identity/threat-model.md)
covers that), what the vended credentials unlock beyond the demo table
(data-layer samples), and the Runtime's own microVM implementation (AWS
shared responsibility; T-24).

## Actors

| Actor | Trust | What they hold |
|---|---|---|
| Tenant user | authenticated, one tenant | an access token with `tenant_id`, `sub`, `client_id`, `scope` |
| Malicious tenant user (same or another tenant) | authenticated | a valid token for tenant B or user A2, and a will to reach A1's unit, data or credentials |
| Internet caller | none | forged, expired or replayed tokens; load |
| Other IAM principal in the vendor account | elevated | an identity policy that allows `bedrock-agentcore:InvokeAgentRuntime`, `bedrock-agentcore:TagResource`, `ssm:PutParameter`, or CloudWatch Logs reads |
| Backend owner (an `AgentBackend` stack's deploying role) | administrative for one backend | through its registry-entry function's role, `ssm:PutParameter`, `GetParameter` and `DeleteParameter` on `<registryPrefix>backends/<name>` for its own name; creates and tags its Runtime (ADR-0024); (v2) its `NAME#<name>` reservation with an owner marker in the entitlement store (ADR-0035) |
| Vendor deployer | administrative | instantiates the construct; owns `tvm.role`, the SSM parameters and the cdk-nag suppressions; can misconfigure |
| The agent itself | caller-influenced | code inside the microVM: the MMDS execution-role credential (logs/traces only), the vended tenant credentials (always present, used for the model call and data), and the transaction token (one tenant, one user, one agent, the granted set, 300 s by default; ADR-0031); a prompt injection or dependency compromise acts with all three, but none reaches another tenant or a shared model |
| Tenant admin (v2) | authenticated, one tenant, scope `entitlements/admin` | an identity token with the admin scope; may write and delete cut rows for users of the tenant the token names, never add (ADR-0033) |
| Vendor control plane (v2) | administrative | SigV4 on the entitlement API's vendor operations: tenant subscriptions and plans (ADR-0030) |
| Tool target owner (a `ToolTarget` stack's deploying role) (v2) | administrative for one target | its Gateway target, its Cedar policy, its `TOOL#<target>` and `NAME#<target>` rows with an owner marker, and `tools/<target>` (ADR-0035) |
| A tool (v2) | caller-influenced | code behind the tools gateway: its own role (no tenant data), the signed tenant context of each call, and the credentials its TVM vends from that context (P-15) |

## Assets and trust boundaries

| Asset | Why it matters |
|---|---|
| Tenant user access token (A-1) | The only source of tenant context (P-3); verified and consumed at the ingress and never forwarded: the agent receives the transaction token instead (A-12, ADR-0031) |
| Unit id, `runtimeSessionId` (A-2) | Names the microVM. Not a secret: the ingress principal, not the id, is the credential (ADR-0002) |
| Tenant-scoped STS credentials (A-3) | 15 to 60 minutes of `TenantId`-tagged access, used for the model call and any tenant data; always in transit through the ingress and the Runtime in a header (ADR-0012, ADR-0018) |
| Execution-role credential, MMDS (A-4) | Readable by any code in the microVM, but grants only logs and traces — no model, no data (ADR-0008 amended by ADR-0018) |
| Ingress role credential (A-5) | The one principal the Runtime trusts; with TVM, the one principal the tenant role trusts |
| Conversation state inside a microVM (A-6) | One tenant user's prompts, model output and memory |
| Tenant data behind the TVM (A-7) | The demo table's `TENANT#<tenantId>` items; whatever a consumer puts behind the same credentials |
| Consumed and published SSM parameters (A-8) | Decide which issuer the ingress trusts and where consumers send tenant tokens |
| Backend registry entries, `<registryPrefix>backends/<name>` (A-10) | Decide which Runtime answers a route and what its agent needs (`needs`, `tools`; ADR-0024, ADR-0032, M-52) |
| Telemetry (A-9) | Must carry `tenantId`, never a token or a credential (P-9). The API Gateway access log also records the source IP and the user's `sub` (`principalId`); a deployer who must not log these two fields changes the access-log format (M-12) |
| Transaction token (A-12, v2) | The only token the agent and the tools see: one tenant, one user, one agent, the granted set, 300 s (ADR-0031) |
| `TokenSigner` key (A-13, v2) | Whoever can `kms:Sign` with it mints any grant for any tenant (ADR-0037) |
| `ToolContextKey` and the signed tenant context (A-14, v2) | The only source of a tool's tenant (P-15); whoever can sign a context reaches any tenant's tool data |
| Entitlement store rows (A-15, v2) | Decide which agents and tools each tenant and user is granted (ADR-0030) |
| JWKS and discovery documents (A-16, v2) | Decide which keys every relying party of the transaction token trusts (ADR-0037) |

## Threats

| ID | Threat | Consequence | Status | Mitigations |
|---|---|---|---|---|
| T-1 | A forged, expired, or ID token, or one signed by an unknown key, is presented as a tenant user (B1) | Acting as a tenant user without a sign-in | Mitigated by design | M-1, M-6 |
| T-2 | A valid token from another app client or another issuer (any Cognito pool in the Region, a vendor-side token) reaches the ingress | Tokens the vendor never meant for the agent are accepted | Mitigated by design: `iss` is pinned to `identity.discoveryUrl`, `client_id` to `identity.allowedClientIds` | M-1 |
| T-3 | A token naming several tenants (a `tenants` claim) or none at all reaches the ingress | The unit, the session tags and the data scope chosen for a tenant the user did not intend, or for no tenant | Mitigated by design; single-tenant users only (spec §1.2, §6.2) | M-1 |
| T-4 | A stolen access token is replayed against the ingress until it expires | The thief opens or resumes that user's conversations as that user, for up to 5 minutes (tenant-identity N-1) | **Accepted**: the token *is* the user for its lifetime. It reaches only that user's own units and data, never another tenant's (M-2, M-3); any vended credential expires with `tvm.durationSeconds` (M-14). Client-side token hygiene and revocation are outside the sample | M-2, M-3, M-14 |
| T-5 | Another IAM principal in the account whose identity policy allows `InvokeAgentRuntime` calls the Runtime directly with any `runtimeSessionId`, bypassing the ingress (V-1) | Any tenant's session reachable without a token; filtered isolation collapses | Mitigated by design; V-1 PASS: an Admin role and a same-account role with an identity-policy allow both get an explicit deny from the resource policy | M-2, M-22 |
| T-6 | A cross-account principal, or any caller using `InvokeAgentRuntimeForUser`, the WebSocket or the `InvokeAgentRuntimeCommand*` variants, reaches the Runtime or its endpoint | A second path into tenant sessions beside the ingress | Mitigated by design: cross-account needs a resource-policy allow that does not exist; the other variants are denied to `*`; V-1 showed the endpoint needs no policy of its own | M-2 |
| T-7 | Tenant B or user A2, holding a valid token, sends A1's unit id in `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` or in the body (ADR-0002, V-3) | Landing in A1's microVM and reading its conversation state | Mitigated by design: the ingress derives the id from the verified claims and ignores (API Gateway) or overwrites (Gateway, V-3) the client's value; residual on the Gateway path is T-11 | M-3, M-2, M-5 |
| T-8 | With session mapping on, two users pick the same `conversationId` (collision, copy or guess) | Two users sharing one unit if the id alone selected it | Mitigated by design: the prefix `sha256(tenant_id\|sub)` qualifies the id per user; the spike saw A2 with A1's `conversationId` land in a different microVM | M-3 |
| T-9 | A `conversationId` sent while session mapping is off, a malformed `conversationId`, or a non-string `prompt` | An accidental shared unit, a Runtime error that leaks internals, or agent input confusion | Mitigated by design | M-3, M-16 |
| T-10 | A token lacking a scope the deployer requires invokes the agent | The deployer's scope-based access control not applying (ADR-0005) | Mitigated when `requiredScopes` is set; off by default (P-4) | M-4 |
| T-11 | The Gateway REQUEST interceptor errors, times out, is throttled, or is detached, and the Gateway forwards the request with the client's own session header | On `agentcore-gateway`, the unit choice (P-2) and the mint and TVM checks skipped: fail-open | **Accepted**: in-code failures short-circuit to 403 (the Gateway returns a `transformedGatewayResponse` without calling the target). The Gateway's behaviour on an *uncaught* interceptor failure is not documented and was not spiked, so `agentcore-gateway` carries the larger residual and the README says so. Alarm on interceptor errors and throttles. **Follow-up**: an integ probe that throttles the interceptor (reserved concurrency 0) and asserts the Runtime is not invoked; `scripts/integ.sh` has no such step yet | M-5, M-2, M-22 |
| T-12 | On API Gateway, a cached authoriser result is reused for a different token, or a method exists without the authoriser | A request passing the integration Lambda with stale or absent claims | Mitigated by ADR-0015 (cache length amended by ADR-0023, cache key by ADR-0024): the authoriser result cache is 300 s and keyed on the whole `Authorization` header and the request path (`context.path`), so a cached Allow applies only to the same token on the same route and is at most 300 s stale; the integration Lambda re-verifies the token, including `exp`, before any invoke; one method; claims read only from the authoriser context. (Amended 2026-11-04, ADR-0043) The cache is at most 60 s, `min(60 s, transactionToken.ttl - 120 s)`, because in v2 the cached Allow carries a minted transaction token; with `identity.multiTenant` `X-Tenant-Id` is part of the key (T-93) | M-6, M-1, M-75 |
| T-13 | Code in the microVM (prompt injection, dependency compromise, tool bug) reads the execution-role credential from MMDS and uses it (ADR-0008) | Whatever the execution role can reach is reachable by caller-influenced code | Mitigated by design: since ADR-0018 the role can write logs and traces only — no model and nothing tenant-scoped (P-6). The model is reachable only with the vended per-tenant credentials, so a stolen execution-role credential cannot even run up model cost. `requireMMDSV2` is deferred until CloudFormation exposes it (ADR-0026) | M-7, M-15 |
| T-16 | The deployer's `tvm.role` trust policy trusts more than `tvmCallerRole`, omits the `TenantId` request-tag condition, or leaves `aws:TagKeys` open (ADR-0012) | Any principal that can call `sts:AssumeRole` reads every tenant's data | **Accepted, deployer-side**: the construct grants only its half (the ingress role's `AssumeRole`/`TagSession` on `tvm.role`) and cannot validate a role it does not own. The contract is spec §6.1, the demo ships a correct role, integ step 8a proves the runner is refused, and the hardening checklist names the review. **Riskiest deployer-side item** | M-10, M-22 |
| T-17 | Tag injection through `tvm.claimTags`: a mapped claim the user influences, or a `claimTags` key of `TenantId` or `UserId` | ABAC conditions keyed on the injected tag granting another tenant's data | Mitigated by design: reserved keys fail synth; values come only from the verified payload; a missing claim is 403; the deployer is told to map only claims the identity provider sets from vendor data | M-11, M-10 |
| T-18 | A hop on the path logs request header values (API Gateway data trace or access-log format, interceptor log, Runtime or OTEL streams), recording the credential or transaction-token header (V-7) | Live tenant-scoped STS credentials, or a bearer token, in a log for anyone with Logs read | Mitigated by design and verified: the V-7 sweep found zero hits for `ASIA`, `secretAccessKey`, the base64 credential prefix, the header name and a JWT prefix across every log group. `dataTraceEnabled` MUST stay off; the agent and OTEL MUST not record headers. Amended 2026-11-06: a custom resource that runs after the Runtime puts a 30-day retention and a data protection policy on the Runtime's own log group (the service creates it at `CreateAgentRuntime`, so a stack cannot own it as an `AWS::Logs::LogGroup`); the policy masks, at ingest, any JWT, the base64 credential header, and the decoded credential object's `secretAccessKey` and `sessionToken` fields (ADR-0047), so an agent that goes rogue and logs a header value hands it only to a reader who also holds `logs:Unmask`; audit hits show in the `LogEventsWithFindings` metric. The V-7 sweep reads the Runtime groups with `--unmask` (a masked read would hide a leak) and checks `LogEventsWithFindings` over them is 0; integ step `mask` proves the patterns on CloudWatch's engine with probe lines each run. Residual: a later deployer change; `logs:Unmask` holders; unit tests pin the stage settings and the policy | M-12, M-67 |
| T-19 | A tenant is offboarded or a user disabled while vended credentials are still valid in the microVM or the ingress cache | Data access continues for up to `tvm.durationSeconds` after the identity provider stopped issuing tokens | **Accepted**: STS credentials cannot be recalled before expiry short of a deny on the role. New vends stop at once because the token is re-verified per request; the window is 15 minutes by default, 1 hour at most. An offboarding runbook that attaches a `TenantId` deny to the tenant role is a deployer action | M-14, M-13 |
| T-20 | The credential cache serves credentials vended for a different tag set (key incomplete when `UserId` or `claimTags` are on, or an entry mutated after insertion) | Cross-tenant or cross-user credentials from the ingress | Mitigated by design: the key is the canonical JSON of the full session tag set, sorted by key (`sessionTags`); each `TokenVendingMachine` serves one `tvm.role`, so the role is not part of the key; an entry is replaced, never mutated | M-13, M-11 |
| T-21 | Many distinct tenants or users, or forced cache misses (cold starts, many Lambda environments), drive `sts:AssumeRole` past the account's STS limit | Every tenant's TVM path fails with throttling: denial of service through the TVM | **Accepted**: the cache keeps STS at about one call per tenant (or user) per lifetime per Lambda environment (V-7: one `AssumeRole` per tenant, not per request), but STS limits are per account and shared, and `includeUserIdTag` multiplies the key space. Narrowed by T-36 (ADR-0022) | M-13, M-19, M-26 |
| T-22 | Prompt injection persuades the agent to read `TENANT#<other>` or to name another tenant in a tool call | Another tenant's data in the response, if code rather than IAM were the wall | Mitigated by design: the agent only holds credentials tagged with the caller's `TenantId`, has no `sts:AssumeRole` of its own, and the cross-tenant read fails in IAM (V-7: `AccessDeniedException` from DynamoDB). Prompt injection can waste tokens, not cross tenants | M-15, M-10, M-7 |
| T-23 | With `session.scope: 'tenant'`, any user of the tenant resumes a conversation another user of the same tenant started | Users within one tenant reading each other's conversations | (v2: `'tenant'` becomes the default once `session` is set, ADR-0039; see T-81) **Accepted by design**: that scope trades user separation inside a tenant for fewer cold starts (ADR-0002); when `session` is set, `'tenant'` is the default and `'user'` is the opt-in (ADR-0039; corrected 2026-11-04, the row said the reverse); the README states it | M-3 |
| T-24 | The Runtime fails to isolate or sanitise a microVM | A cross-session leak below the sample's control | **Accepted**: service boundary (shared responsibility). The sample gives the agent a data-free role so a breach gains nothing tenant-scoped (`requireMMDSV2` is not yet exposed by the CloudFormation resource and is deferred, ADR-0026); everything tenant-scoped the agent holds expires with the token or the credential | M-7 |
| T-25 | An agent answer outruns an intermediate hop's timeout, or many long streams are opened (V-4, V-5) | Truncated answers reported as success; the API Gateway integration Lambda held for the whole stream | Mitigated: timeouts aligned end to end (V-5: 29 s cut the stream, 2 min did not); the cost of long streams on API Gateway is measured and reported (ADR-0009) | M-17, M-19 |
| T-26 | One tenant's script saturates the shared Runtime, the Lambda concurrency or the Bedrock model quota | Every other tenant throttled: a noisy neighbour in the pool model | **Accepted**: API Gateway has a stage throttle and can take WAF and per-tenant usage plans (tenant-identity ADR-0025 is the worked example); `agentcore-gateway` has no per-tenant throttle in this sample and the Gateway's and Runtime's quotas apply to all tenants together. Hardening checklist item. Narrowed by T-35 (ADR-0020) | M-19, M-18, M-25 |
| T-27 | Raw tokens, prompts or tenant identifiers written to logs as free text | Logs become a credential or conversation store | Mitigated by design | M-12, M-18 |
| T-28 | The session prefix in Runtime log stream names and ingress logs is inverted to `tenant_id` and `sub` | Pseudonymous identifiers resolving to users | **Accepted**: the prefix is a truncated SHA-256, logged next to `tenantId` at the ingress on purpose so a session joins back to a tenant (P-9). `tenant_id` is an opaque ULID and `sub` an opaque Cognito id, not personal data | M-24 |
| T-29 | A principal with `ssm:PutParameter` on `/application-plane/shared/identity/*` points `userPoolId` or `appClientId` at an issuer it controls before the demo stack is synthesised | The ingress trusts an attacker's issuer on the next deploy | **Accepted**: the demo resolves the parameters at deploy time (CloudFormation SSM parameter values), so a deploy reads whatever value the path holds then; nothing checks that the pool is tenant-identity's. The guard is account IAM on the shared parameter path, outside the sample; the construct itself reads no SSM, so a consumer wiring its own issuer is unaffected | M-20, M-1 |
| T-30 | A principal with `ssm:PutParameter` on `/application-plane/shared/agent-runtime/*` replaces `endpointUrl` or `runtimeArn` | A later consuming sample sends tenant tokens and prompts to an attacker's endpoint | **Accepted**: same guard as T-29; consumers are told to check the account in `runtimeArn`. The v2 document's key and gateway fields are T-104 | M-20 |
| T-31 | A cdk-nag suppression relaxes a control without a stated reason, or the build's placeholder context reaches a real deployment | A mitigation believed present but absent | Mitigated by design | M-21 |
| T-32 | A bug or compromised dependency in the integration or interceptor Lambda runs code with the ingress role | `InvokeAgentRuntime` for any session, and with TVM `AssumeRole` on the tenant role with any tag: the one trusted principal turned against every tenant | **Accepted**: this is the pattern's cost (ADR-0001). The ingress is by design the one principal that can reach every session and every tenant's data role; pinned dependencies, refusal tests and CloudTrail detection bound it, nothing removes it. **Highest-consequence accepted item** | M-22, M-10 |
| T-33 | After an incident, a Runtime session, an `AssumeRole` or a Bedrock call cannot be attributed to a tenant | Isolation that cannot be shown to have held, nor billed or throttled per tenant | Mitigated: `tenantId` in ingress logs and metrics, session name `tenant-<tenant_id>` on `AssumeRole`, hash prefix on Runtime streams; what the Runtime cannot carry is listed in `architecture.md` | M-18, M-22 |
| T-34 | `cdk destroy` leaves the Runtime, a log group, the demo table or a parameter behind | Residual tenant data and a reachable Runtime in an account believed clean | Mitigated by design | M-23 |
| T-35 | One tenant's script uses up the shared stage throttle, the AgentCore Runtime session or TPS quota, or the account's Bedrock quota (narrows T-26) | Every other tenant gets 429s or throttling: a noisy neighbour in the pool | Mitigated by ADR-0020: a fleet-wide per-tenant request limit (60 per minute by default) and an optional output-token limit, checked before STS and the Runtime. **Residual accepted**: up to 2x the limit across a window boundary; fail-open on a DynamoDB error; no token limit on `agentcore-gateway` | M-25, M-19 |
| T-36 | TVM fan-out or a cold-start herd (many instances, many tag sets, `includeUserIdTag`) drives `sts:AssumeRole` past the account's 600 rps (narrows T-21) | Every tenant's request fails at the TVM | Mitigated by ADR-0022: a bounded LRU cache, one STS call per tag set per instance through single flight, and the ADR-0020 limit before STS. **Residual accepted** when an instance serves more active tag sets than `tvm.cacheMaxEntries` | M-26, M-25 |
| T-37 | A tenant forges or inflates another tenant's limit counter to lock it out | Another tenant limited (429) without having sent requests | Mitigated by design: the counter key is built from the verified `tenant_id` only, never from the request; only `tvmCallerRole` has `dynamodb:UpdateItem` on the table | M-27, M-1 |
| T-38 | Per-tenant metrics left on at many tenants (up to 9 x (1 + backends) custom metrics per tenant per ingress: 9 metrics under `[TenantId, Ingress]` plus 9 under `[TenantId, Ingress, Backend]` for each backend) | A CloudWatch bill that grows with tenants: 10,000 tenants on one ingress with two backends is 9 x 3 x 10,000 ≈ 270,000 custom metrics; see [CloudWatch pricing](https://aws.amazon.com/cloudwatch/pricing/) | Mitigated by ADR-0021: off by default; a synth warning when on; the log line carries the same figures for Logs Insights and Contributor Insights | M-28 |

## Accepted risks

Listed in order of consequence. Each is on the README's production hardening
checklist unless marked "by design".

- **T-32, ingress compromise.** The ingress is the one principal the Runtime
  trusts and, with TVM, the one principal the tenant role trusts. That is
  what makes a leaked JWT useless (ADR-0001) and also what makes a bug in the
  integration or interceptor Lambda a boundary-wide bug. Pinned dependencies,
  one unit test per refusal, and CloudTrail alarms on any other principal
  calling `InvokeAgentRuntime` or assuming the tenant role bound it. Nothing
  removes it; a backend with native principal-to-unit binding would (ADR-0001
  "revisit").
- **T-52, signing-key misuse (v2, ADR-0031, ADR-0037).** Whoever can
  `kms:Sign` with the `TokenSigner` key mints a token for any tenant, user,
  agent and grant. `kms:Sign` is granted only in the key policy, to the
  minting role; grants are denied in the key policy, so no IAM policy can
  add a signer; the private key cannot leave KMS, and alarms watch the
  `Sign` rate and errors. The minting role is the ingress, so this widens
  T-32 rather than adding a new principal; the other path is
  `kms:PutKeyPolicy`, held by the account's key administrators (the
  deployer's own privilege, T-97). CloudTrail on `Sign` by any other
  principal, and on `PutKeyPolicy`, is the detection.
- **T-97, `kms:PutKeyPolicy` on the signer keys (v2, 2026-11-04).** Whoever
  may rewrite the key policy of `TokenSigner` or `ToolContextKey` can add a
  signer. That is the deployer's own administrative privilege, which
  CloudFormation needs; the key policy leaves no other path (M-78).
- **T-100, the authoriser-context path at the `scope` bound (v2,
  2026-11-04).** Mitigated 2026-11-04 (was open): spike V-17 found the
  authoriser context is not a limit (24,000 bytes passed) and the Runtime's
  10,240-byte header cap is; the mint enforces it (M-81, ADR-0045).
- **T-101, the Runtime's documented header limit (v2, V-17, 2026-11-04).**
  The Runtime enforces 10,240 bytes per custom header value and documents
  4 KB. The sample relies on the enforced value; if AWS tightens it, tokens
  over 4 KB fail at the Runtime with a 400 (a refusal, never a wider grant).
  Watch the Runtime `ValidationException` rate; the fix is one constant,
  `MAX_TOKEN_BYTES`.
- **T-84, tools interceptor compromise (v2, ADR-0034).** The tools-side twin:
  the interceptor alone signs tenant contexts, and a context is what a tool's
  TVM trusts. Pinned dependencies, a minimal bundle and a `Sign` alarm on
  `ToolContextKey` bound it; nothing removes it.
- **T-85, the per-tool wall is vendor code (v2, ADR-0041).** Policy decides
  per target, so inside a target a user partly holds, the interceptor alone
  refuses a tool `scope` does not name. A bug there lets a user call a tool
  of their own tenant they were cut from; it never crosses tenants. Unit
  tests per refusal, fail-closed, logged refusals and integ step 22 bound
  it. Per-tool policies would remove it and were rejected for their deploy
  time and quota (ADR-0041 option 1).
- **T-89, rate-limit budget per gateway (v2, ADR-0041).** A tenant's tool
  rate limit applies on each tools gateway, not across them. Availability
  only, as T-73.
- **T-94, the 60 s Gateway refusal margin and the authoriser cache (v2,
  ADR-0043, 2026-11-04).** A tools gateway refuses a token with 60 s or
  less left, and on `api-gateway` a cached decision can hand out the same
  transaction token for up to 60 s. The reuse margin (cache TTL plus the
  longest stream) keeps a stream's tool calls inside the token's usable
  life; the margin only shortens how long a token in flight is honoured.
- **T-96, orphaned Gateways and Policy engines after a failed teardown (v2,
  2026-11-04).** Empty of targets and policies, they serve nothing and deny
  everything, but count against quotas until the `DELETE_FAILED` stack is
  deleted again. The integration driver retries the teardown and fails the
  run on a leftover stack.
- **T-16, tenant role trust widened by the deployer.** The construct grants
  only its half of the TVM contract. A `tvm.role` that trusts a second
  principal, drops the `TenantId` request-tag condition, or leaves
  `aws:TagKeys` open silently makes every tenant's data readable by anyone
  with `sts:AssumeRole`. The demo ships a correct role and the integration
  test proves the runner is refused, but the sample cannot validate a role it
  does not own.
- **T-76, tool tenant role trust widened by the deployer (v2).** As T-16,
  for each `ToolTarget.tvm.role`: the construct cannot validate a role it
  does not own; spec §6.1 is the contract and integ step 20 the proof.
- **T-11, Gateway interceptor fail-open on an uncaught failure.** In-code
  failures short-circuit to 403. What the Gateway does when the interceptor
  Lambda times out or is throttled is not documented and was not spiked,
  and the integration test has no throttle probe yet (follow-up). So
  `agentcore-gateway` carries a larger residual than `api-gateway`, and the
  README comparison says so (ADR-0009).
- **T-39, registry as a trust boundary (ADR-0024).** Whoever can
  write `<registryPrefix>backends/<name>` chooses the Runtime that answers
  that route and the scopes it needs. The write grant is on each backend's
  registry-entry function role and names one parameter, a Create refuses an existing name and a Delete drains only its
  own entry, the ingress reads only and rejects a `runtimeArn` outside its
  own account and Region, and a wrong entry reaches the wrong backend, never
  another tenant's data, because credentials and session prefix come from
  the verified claims. Residual: a principal who already holds
  `ssm:PutParameter` on the prefix (the T-29, T-30 guard) can overwrite a
  route to another Runtime in this account that trusts this ingress; CloudTrail on
  `PutParameter` under `backends/` is the detection.
- **T-40, tag-conditioned invoke grant (ADR-0024).** The ingress
  role's grant is a Runtime ARN pattern with an `aws:ResourceTag/ri:ingress`
  condition, not a list, so the Runtime resource policy (P-1) is the hard
  gate; the policy names the Runtime ARN, the one the ingress invokes by.
  Residual: a Runtime owner who both tags their Runtime with this
  ingress's id and names the ingress role in its policy makes it reachable,
  but only through a registry entry (T-39). `TagResource` on Runtimes is held
  by the backend-deploying roles and account administrators, not the ingress
  role.
- **T-82, third-party targets under 2LO or an API key (v2).** One
  vendor-shared credential reaches the third party for every tenant, so
  isolation there is filtered and the README says so; 3LO or OBO where the
  system offers it.
- **T-29, T-30, SSM parameter tampering.** Anyone with `ssm:PutParameter`
  on `/application-plane/shared/*` can repoint the issuer before a deploy or
  redirect a consumer. Shape checks at synth stop malformed values, not a
  swap for another real pool. The control is account IAM on the shared path.
- **T-26, T-35, noisy neighbour.** Pool model, one Runtime, one model quota.
  Since ADR-0020 each tenant has a fleet-wide request limit (60 per minute by
  default) on both ingresses, checked before STS and the Runtime. Residual: a
  tenant can reach up to twice the limit across a window boundary; a DynamoDB
  error admits requests (fail-open, so a DynamoDB fault is not an outage);
  `agentcore-gateway` has no output-token limit, because the interceptor never
  sees the response.
- **T-73, tools gateway rate limits (v2).** Keyed on the verified
  `tenant_id`, fail-open by the service's design: fairness, never isolation.
  The 200 TPS per Gateway and per account is shared by every tenant.
- **T-62, KMS `Sign` throttling (v2).** One `Sign` per mint-cache miss, on a
  per-Region quota shared with everything else in the account. Refused and
  limited requests never reach KMS; V-12 measures the real rate.
- **T-21, T-36, STS throttling through the TVM.** Since ADR-0022 the cache is
  bounded and concurrent misses share one STS call, and limited requests never
  reach STS. Residual: an instance serving more active tag sets than
  `tvm.cacheMaxEntries` calls STS more often; STS limits are per account and
  `includeUserIdTag` multiplies the key space. Size the bound to active
  tenants per instance.
- **T-38, per-tenant metric cost.** By design off; a deployer who turns
  `perTenantMetrics` on accepts up to 9 x (1 + backends) custom metrics per
  tenant per ingress (about 270,000 at 10,000 tenants with two backends), and
  the synth warning says so.
- **T-19, credential lifetime vs offboarding.** Vended credentials live up
  to `tvm.durationSeconds` (900 by default, 3600 at most) after the identity
  provider stops issuing tokens; recall needs a deny on the tenant role.
- **T-4, stolen token replay.** The token is the user for its 5-minute
  life; it reaches only that user's own units and data.
- **T-53, stolen transaction token (v2).** The token is the user acting
  through one agent for its life, 300 s by default; it cannot be refreshed,
  and no revocation in flight exists (ADR-0036 names a `jti` denylist and
  does not build it).
- **T-79, key rotation window (v2).** An old `kid` stays trusted for one
  token life after a bump; emergency removal is a second bump.
- **T-24, microVM isolation itself.** Service boundary; the sample ensures a
  breach gains nothing tenant-scoped beyond what the session already held.
- **T-23, `session.scope: 'tenant'`.** By design: an explicit trade, off by
  default.
- **T-81, `session.scope: 'tenant'` as the default (v2, ADR-0039).** By
  design once `session` is set: colleagues share a conversation. The agent
  MUST read the transaction token from each request and never from unit
  state; an agent that caches it is the residual.
- **T-67, wrong own-tenant selection (v2, ADR-0038).** A client bug can act
  for the user's other tenant; never for a tenant the user is not in.
- **T-28, session prefix as a pseudonym.** By design: the join to `tenantId`
  at the ingress is the attribution P-9 requires.
