# ADR-0052: Run the stress test as a slice of the platform stress contract

- Status: Accepted
- Date: 2026-11-19
- Amends: the stress-test plan (`design/agentic-runtime-isolation.stress-test.md`, §8)
- Amended by: ADR-0054
- Deciders: Dave Roberts (PSA)

## Context
The sample's stress test was a row of scripts an operator ran by hand (`deploy.sh`, `seed.sh`, `run.sh s1`, `collect.sh <run id>`, `teardown.sh`). The platform stress test (`docs/stress-test.spec.md` §3.4, work item W-3) runs every sample through one contract: `scripts/stress/slice.json` and `slice.sh` with six verbs, the `STRESS_*` environment, one result record per scenario, a quota budget, and a runner that deploys, runs and tears down in order. Six choices were not obvious.

1. **Which tier table.** The contract's tiers (`stress/src/tiers.ts`) size a cell (`agentsPerCell`, `toolTargetsPerCell`). This sample's table (`test/stress/tiers.ts`) sizes one ingress that holds the whole load: 100 agents and 1,000 tools at `large`, as its earlier runs measured them.
2. **Which identity.** Stress ADR-0002 gives the platform run its own `tenant-identity` pool. This sample's integration and stress tests have always reused the long-lived `TenantIdentity-shared-pool` deployment.
3. **Where state lives.** The scripts kept their outputs, manifest and timings in `~/.runtime-isolation-stress/<prefix>/`. The contract keeps manifests under `$STRESS_HOME/<prefix>/`.
4. **Who writes the record.** The k6 library (stress ADR-0008) writes each record from `handleSummary` with every 4xx and 5xx the driver saw as `unattributed`. Only the hops' logs say which tenant a refusal belonged to.
5. **What happens to the tenants.** Stress ADR-0004 keeps a fleet only when the tier onboards once (`large`).
6. **Platform mode.** In the platform run the control plane deploys the cells (W-5); this slice has nothing to deploy there yet.

## Options considered
### Option 1: Port the scripts to the contract, keep the sample's tiers and identity
Pros: the 2026-11 runs stay comparable (same agents, tools, reserves); no new identity deployment; the shipped scripts keep their tested behaviour. Cons: at `medium` and `large` the slice stresses one big ingress while the platform run stresses several small cells, so per-cell numbers are not comparable across modes (stress ADR-0003 says as much); the shared pool's 10,000-group cap applies.

### Option 2: Rebuild the slice on the contract's per-cell tiers and the stress identity
Pros: one meaning of a tier everywhere. Cons: loses the comparison with the earlier runs; the stress identity belongs to the `tenant-identity` slice (W-6), which this slice would then depend on in slice mode too.

### Option 3: Keep the manual scripts beside a thin slice
Pros: nothing is removed. Cons: two ways to run the same scenario, one of them copying files through S3 and polling SSM by hand; the second goes stale.

## Decision
Option 1.

- **Tiers and identity.** The slice reads the sample's tier table; the shared figures (tenants, users, rates, scenario length, driver size) still come from `stress/src/tiers.ts`. In slice mode identity is the published `TenantIdentity-shared-pool` deployment: the slice reads its parameters, registers the vendor scopes it needs (`app/use`, `entitlements/admin`), creates and deletes its own tenants, and never deploys, replaces, updates or destroys the stacks. `slice.sh` refuses a prefix that starts with `TenantIdentity`. Stress ADR-0002's own pool is for the platform run.
- **State.** `slice.sh` exports `STRESS_STATE_DIR=$STRESS_HOME/$STRESS_PREFIX/agentic-runtime-isolation/`, and `deploy.sh`, `seed.sh`, `teardown.sh` and `count.sh` use it when set and `~/.runtime-isolation-stress/<prefix>/` otherwise. It holds a folder, not one file, because it holds stack outputs, a manifest and timings.
- **Run.** `slice.sh run S<n>` calls `stress/driver/k6.sh` with the sample's tier JSON as `STRESS_TIER_JSON` (the scenarios read `agents`, `tenantLimitRpm` and the reserves from it) and the seed manifest as an input file. `run.sh`, which uploaded to S3 and polled SSM itself, is deleted. S2's recipe (new Lambda instances, authoriser cache flushed, 60 s idle) moved into `slice.sh`. S2 reuses S1's warm conversations because every scenario of a run shares the run id that names them, so `CONVERSATION_RUN_ID` is not needed; `slice.sh run S2` exits 2 with a message when the run holds no S1 record, because S2 without them opens a new Runtime session per tenant at the herd rate, which tests the session-creation quota (plan F-2) rather than the cold ingress.
- **Pass criteria.** Spec §3.4 has `run` exit non-zero on a failed pass criterion. `run` does for the criteria k6 can decide on its own: the isolation mismatch, the positive control and S3's delivery (`steady_sent` at least 95 % of `steadyRps × seconds`) are k6 thresholds. The other rows (P-7, 429 attribution, S3's noisy-only row, 5xx, the throttle rows, the CloudWatch minutes, P-10) are decided in `collect`, on purpose: they read log lines and metrics that settle minutes after the scenario ends (Logs Insights lags about two minutes, API Gateway stamps a minute late), which `run` cannot wait for without spacing every scenario further. A failed row makes `collect` exit 1, which fails the run.
- **Collect.** For each record it wrote, `collect.sh` reads the window the record names, queries `request refused` lines by tenant and reason on the authoriser and ingress log groups, and sets `refusals` from them (`attribute.jq`): the lines that carry a tenant are `byTenantReason`; what the driver saw beyond them is `unattributed`. The driver's count comes from the k6 summary only; without it `refusals` stays as k6 wrote it and the P-7 row fails, so a second collect cannot read the first one's residual as the driver's count. It also fills `latency.ingress`, `latency.ingress-ttfb` and, in `quotas`, the account's peak Lambda `ConcurrentExecutions` over the scenario's minutes (the figure the quota caps), keeps the sample's pass table (still appended to `design/stress-results/`), and exits 1 on a failed row, so an unattributed refusal fails the run (P-7). It leaves `cost` empty: Cost Explorer settles a day later, and `cost.sh` still reads it then.
- **CloudWatch windows.** CloudWatch at a 60 s period returns the one-minute buckets in `[floor(start), floor(end))`, and API Gateway stamps its datapoints about a minute after the request. With scenarios about 20 s apart, each scenario's query took the previous one's last minute and lost its own (2026-11-19: S4 showed S3's 479 4XX, S7 showed S6's 102). Two fixes were weighed. Moving the 5xx and throttle checks to Logs Insights and keeping the metric rows as INFO cannot see a Lambda throttle, which writes no log line, so the throttle rows would lose their check. Spacing the scenarios keeps every row binding for about seven more minutes a run. `slice.sh run` therefore starts a scenario at least 3 s past the last recorded scenario's metric window and at most 3 s into a minute (this replaces the fresh-limiter-minute wait, which it includes), and `collect.sh` reads each scenario's CloudWatch rows over its own whole minutes: from its start minute to one minute past its end minute (`window.sh`). A `CloudWatch minutes this scenario's own` row fails when the next record started inside those minutes, and the per-minute datapoints are kept in `<scenario>/cloudwatch/` in the run folder.
- **S3 delivery.** S3's VUs pace themselves, and one that falls behind skips the requests it missed. `s3-noisy.js` counts those (`iteration_skipped{reason:behind}`) and the steady requests sent (`steady_sent`) against `steadyRps × seconds` (`steady_expected`); a k6 threshold fails `run S3` at more than 5 % short, and the `S3 steady load delivered` row of `collect` reports the same bound (`delivered.jq`). Each steady VU's rate is its owned tenants' share of the steady rate divided by the VUs in its slot (`k6/noisy-pace.js`), so every steady tenant gets `steadyRps / tenants` and stays under its limit.
- **Budget.** Six draws, all on `cell-account-1`, computed from the sample's tier (`test/stress/slice-cli.ts`): Lambda concurrency (both reserves plus the 100 Lambda keeps unreserved, 1,900 at `large`), STS `AssumeRole` and KMS RSA `Sign` at the peak rate, Runtime invocations at the peak rate, Runtime new sessions at the warm-up rate, and active sessions (twice the active tenants, capped by the seeded). No new quota id: the API Gateway control plane has no Service Quotas code (stress README, known limitations).
- **Tenants.** Teardown deletes the run's tenants when the tier onboards every run (`small`, `medium`) or on `--fixtures`, and keeps the seeded set at `large`, as W-6 does.
- **Teardown.** ADR-0019 holds: the construct owns every log group on its path, so a log group a stack owned that is still there after the destroy is a construct defect. Teardown collects each stack's `AWS::Logs::LogGroup` resources before its destroy and fails on any that remain, and on any other log group named after the slice's stacks (`<prefix>-ingress-…`, `/aws/lambda/<prefix>-ingress-…`, `API-Gateway-Execution-Logs_<api id>`, and the same for the agents and driver stacks); it removes none of them. It removes two kinds of log group no stack owns: the Runtime groups a late line recreated (ADR-0047), and the groups of the CDK's own provider functions (the driver bucket's auto-delete handler, the VPC's default-security-group handler, an `AwsCustomResource` or `LogRetention` singleton, a provider framework's handlers), which the CDK creates with no log group, so Lambda creates `/aws/lambda/<function>` outside the stack when the function runs on the destroy. Teardown finds those functions by logical id in the stack's resource list before the destroy and removes only their groups. Both lists are kept in the state folder (`teardown-state`) with the Runtime ids, the REST API id and the registry prefix, written before the stacks that own them are destroyed and kept until the leftover check passes. A rerun after a teardown that failed or died between destroys therefore still removes the provider groups and the recreated Runtime groups, still names an owned group as a leak, and still checks the agent runtimes, the execution log group and the registry parameters of stacks already gone.
- **Platform mode.** Every verb but `budget` exits 2 with a message when `STRESS_MODE` is `platform`, until W-5 deploys cells and this slice only drives them.

## Consequences
Easier: one command (`stress/run.sh run --tier small --slices agentic-runtime-isolation`) deploys, runs S1 to S7, attributes refusals, tears down and checks for leftovers; the same verbs will run under the platform run once the platform mode exists.

Harder: the slice and the platform run measure different shapes at `medium` and `large` (one ingress against several cells); a refusal that has no log line with a tenant (an API Gateway throttle, a Lambda throttle in S2's herd, a cached authoriser deny) now fails the run as unattributed, where the earlier pass table counted it as expected; `collect.sh` matches refusals to log lines by count, not by correlation id, because the ingress does not log `x-correlation-id` yet (stress ADR-0005, W-8). Each tenant's 429 lines are credited only up to the driver's own 429 count for that tenant (`tenant_429{tenant:<id>}` in the k6 summary, one threshold per tenant the scenario's plan uses, S7's doubled set included), so one tenant's excess lines cannot hide another's unattributed 429; lines with other statuses have no per-tenant driver count and are credited as logged.

Revisit when: the ingress logs the correlation id (join per request, drop the count match); W-5 lets the platform run deploy this sample as a cell (platform mode, the stress identity); or a slice run at `medium` shows the 10,000-group cap of the shared pool in the way.
