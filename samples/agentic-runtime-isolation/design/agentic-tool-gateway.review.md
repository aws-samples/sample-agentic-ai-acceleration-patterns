# Multi-tenant tool gateway for agentic applications: feature review

> Status: Historical. Folded into `agentic-runtime-isolation.spec.md` v2
> (ADR-0034); no separate spec exists. Review of the proposed feature list,
> 2026-10-30. Research: AgentCore Gateway developer guide, quotas and pricing
> pages as of 2026-10-30.

## 1. What the sample is

One shared AgentCore Gateway is the MCP server every agent in the
application calls for tools. The vendor owns the Gateway and every target.
A tenant user's token decides which tools the agent sees and may call, how
fast, and which tenant's data a tool reaches. Tools are added, changed and
removed without touching the Gateway.

Pool model: one Gateway, one set of targets, every tenant. The agent that
calls it is a consumer (`agentic-runtime-isolation` forwards the user's
token on opt-in, its ADR-0006). Identity is `tenant-identity`'s token
contract; any OIDC issuer works because the Gateway's `CUSTOM_JWT`
authoriser takes a discovery URL.

Item 2, "I think this is list_tools": half. Filtering `tools/list` hides a
tool; refusing `tools/call` is the wall. Policy does both from the same
rule. A design that only filters the list is filtered isolation (ARCHITECTURE
§3.2) and is not enough.

## 3. The request path

```
agent ──tools/call──▶ Gateway: JWT verify ──▶ Policy: scope permits <target>___<tool>? ──▶ REQUEST interceptor
                                   (native)                 (native, default deny)              re-verify token
                                                                                                scope check again
                                                                                                sign {tenant_id, sub, tool, argsHash, exp 60 s}
                                                                                                write log line
                                                                                            ──▶ Lambda tool: verify signature (cached public key)
                                                                                                TVM: AssumeRole + TagSession TenantId   (cached)
                                                                                                data call with tenant credentials
                                                                                                write metering line
```

`tools/list` stops at Policy: the caller sees the tools it may call. No
interceptor runs for a denied call, so the interceptor's log line is the
"admitted" line; refusals are the Gateway's `UserErrors` metric and the
Policy decision logs, which carry no tenant. Spike V-4 confirms the order.

## 4. Why the tenant context is signed

The Gateway invokes a Lambda target with its own service role. The event is
the tool's arguments; the client context names the Gateway, target and tool,
and nothing about the caller. Lambda targets allow no header, no token
passthrough and no caller credentials. The REQUEST interceptor sees the
bearer token (`passRequestHeaders`) and may rewrite the arguments. A tenant
id written as a plain argument could also be written by the client, and the
tool could not tell the two apart.

So the interceptor writes a compact signed context (KMS asymmetric key,
`Sign` per call, 60 s expiry, bound to the tool name and a hash of the
arguments) into a reserved argument, overwriting whatever the client sent.
The tool verifies it with the key's public half, fetched once per process,
and only then calls the TVM with the tenant id from the context. A tool that
receives no valid context has no credentials: its own role reaches no tenant
data (runtime-isolation ADR-0008). Credentials themselves never travel in
the request body: they would land in vended logs and tool event logs.

Reviewed alternatives, each rejected in an ADR:

- **Credentials in the body.** Fewer hops, but a credential in every request
  log; and the 6 MB and `requestBody` logging make it worse, not better.
- **OBO token exchange against tenant-identity's RFC 8693 endpoint.** The
  cleanest shape for an MCP-server target the vendor owns: the target gets
  a narrowed tenant-identity token and verifies it like any ingress. Lambda
  targets cannot use it; keep it as the MCP-server variant of the same
  verifier if spike V-3 passes.
- **One Gateway per tenant.** Silo. 1,000 Gateways per account, one rate
  bucket each, no shared targets; every tool change is N deploys. The
  isolation gain is nil because the Lambda still runs as the Gateway role.
- **Interceptor-only entitlement** (RESPONSE interceptor filters the list,
  REQUEST interceptor refuses the call). No Policy cost, but two Lambda
  invocations per `tools/list`, and the wall is vendor code. Kept as the
  defence-in-depth check the interceptor already performs for free, since it
  must verify the token anyway.

## 5. Review

### 5.1 Performance

| Step | Cost per call | Note |
|---|---|---|
| JWT verify, Policy | native, single-digit ms | Policy evaluation latency unpublished; measure in the spike |
| REQUEST interceptor | ~5 ms warm, 100 to 500 ms cold; plus KMS `Sign` ~10 to 20 ms | Provisioned concurrency on the interceptor; one interceptor per Gateway, so it is a shared hot path |
| Lambda tool | its own; TVM `AssumeRole` only on cache miss | Same bounded single-flight cache as runtime-isolation ADR-0022 |
| RESPONSE interceptor | one more Lambda invocation | Off by default; only for third-party targets whose latency and status the tool cannot log |
| `tools/list` | native; 30 tools per page, cursor | Agents must cache the list; polling it is the known noisy-neighbour source |
| Semantic search | 25 calls per minute per account (adjustable), $0.025 per 1,000 | Off by default |

Per-call price: Gateway $0.005, Policy $0.025, KMS $0.003 per 1,000 calls,
plus the two Lambda invocations. Policy is the largest line; the ADR says
so and names the interceptor-only fallback.

### 5.2 Simplicity

Items 1, 3, 5, 6 and the enforcement half of 2 are native. Vendor code is
four pieces: the `ToolTarget` construct (target, scope registration, policy
template), the interceptor (verify, scope check, sign, log), the tool-side
library (verify, TVM, metering line), and the demo tools. Nothing is
reimplemented that the Gateway does: no DynamoDB limiter, no registry of
targets (the Gateway is the registry).

Reuse: tenant-identity's catalogue and token exchange as they are. The TVM
and verifier code exists in `agentic-runtime-isolation` but is not part of
its published interface (`src/index.ts` exports constructs only); either
export a `TenantCredentials` helper there or copy the 150 lines. Decide in
an ADR; the standard prefers the package entry.

### 5.3 Always-enforced isolation

| Layer | Question | Enforced by | Style |
|---|---|---|---|
| Identity | which tenant? | `CUSTOM_JWT`, signature and claims verified by the Gateway and again by the interceptor | enforced, native |
| Entitlement | may this user call this tool? | Policy, default deny, from the `scope` claim the identity provider issued; the interceptor repeats the check | enforced, native |
| Provenance | is this tenant id the one the token carried? | KMS signature over `{tenant_id, sub, tool, argsHash, exp}`; the tool refuses a missing, expired or mismatched context | enforced, vendor code |
| Data | which tenant's data may the tool read? | TVM, `TenantId` session tag, ABAC on the data store; the tool's own role has no tenant data | enforced, IAM is the wall |
| Invocation | who may run the tool? | Lambda resource policy: the Gateway role only; the Gateway role: the registered tool functions only | enforced, native |
| Third party | whose credential reaches the external system? | 3LO or OBO: the user's, keyed by the inbound token in the vault. 2LO or API key: the vendor's, shared | enforced for 3LO/OBO; shared and named as such otherwise |
| Fairness | how much may one tenant use? | native rate limits per `tenant_id`; fail-open | availability, not isolation |

Where a bug could cross tenants, and why it does not:

- The interceptor derives `tenant_id` from the token it verified, never from
  the body; a client-supplied context is overwritten.
- A tool that ignores the context gets no credentials, not the wrong ones.
- A tool with the wrong tenant id in its context would need a forged
  signature.
- Policy failing is a deny. Rate limits failing is an allow, which is why
  they are not an isolation control.
- The interceptor is one Lambda for the whole Gateway: a failure there is a
  Gateway error after retries, not a bypass (spike V-5 confirms fail-closed).

What stays filtered: a third-party OpenAPI or MCP target under 2LO. The
README says that any tenant row such a system returns is the vendor's to
scope, and recommends 3LO where the system offers it.

### 5.4 Scale limits

Documented quotas on 2026-10-30, all adjustable unless noted. Check Service
Quotas for the account and Region.

| Limit | Value | What hits it | What the sample does |
|---|---|---|---|
| Gateways per account | 1,000 | gateway-per-tenant designs | one Gateway |
| Targets per Gateway | 100 | one target per team or service | `ToolTarget` groups tools per service; the construct refuses the 101st at synth only if it can count, otherwise the deploy fails |
| Tools per target | 1,000 | large OpenAPI specs | none needed |
| Tool-call and tool-list rate | 200 TPS per Gateway **and** per account | every tenant together; `tools/list` polling | per-tenant limits bound one tenant's share; README asks for the increase first |
| Concurrent connections | 5,000 per Gateway and per account | long tool calls: connections = TPS × call seconds | the 15-minute invocation timeout makes this the real ceiling for slow tools |
| Semantic search | 25 per minute per account | agents searching per turn | off by default |
| Payload | 6 MB per call, list or search | large tool results | tools page their own results |
| Interceptors | 1 REQUEST + 1 RESPONSE per Gateway | every feature wanting a hook | one interceptor does verify, sign and log |
| Rate limits | 50 per Gateway, 1,000 entries each, 10 dimension keys | per-tenant tiers | `*` bucket for everyone, explicit entries for named tiers; 50 × 1,000 named tenants at most |
| Target operations | 5 TPS; 5 concurrent per Gateway | a pipeline deploying many tool stacks at once | document; CloudFormation retries |
| Policy | per-request charge; count limit unpublished | O(targets) policies by design, never O(tenants) | one policy per target, generated |
| Token size | Cognito `custom:scopes` 2,048 chars; access token in an HTTP header | a user entitled to many tools | scopes name a target or a tool group, not every tool |
| Identity (3LO, OBO) | 200 TPS each for `GetWorkloadAccessTokenForJWT` and `GetResourceOauth2Token`; 50 API-key providers per account | per-user third-party calls | one provider per target; cached tokens in the vault |
| STS `AssumeRole` | 600 rps per account per Region, shared | tool TVM cache misses: instances × tenants ÷ TTL | bounded cache, single flight (as ADR-0022) |
| KMS `Sign` | per-Region request quota, shared | one per admitted call | the one call that scales 1:1 with traffic; named in the README |
| Lambda concurrency | account-wide | interceptor + tools, held for the tool's duration | provisioned concurrency on the interceptor; reserved concurrency per tool is the tenant-fairness knob the Gateway lacks |
| Cross-Region targets | not supported | multi-Region fleets | one Gateway per Region |
| Policy and new tools | known defect: tools added after a policy is written are denied until a no-op `UpdatePolicy` | every `ToolTarget` deploy | the construct's custom resource touches the policy after sync |

Entitlement cardinality is the point of the design: the Gateway holds one
policy per target. Who may use it lives in the identity provider as scopes,
so 10,000 tenants and 10,000,000 users cost the Gateway nothing.

## 6. Spikes before the specification is accepted

| # | Question | Decides |

| V-4 | Order of Policy and REQUEST interceptor; does a denied call invoke the interceptor? | where refusals are logged per tenant |
| V-5 | Interceptor timeout or error: Gateway error or pass-through? | the fail-closed claim in §5.3 |
| V-6 | Policy evaluation latency, and `tools/list` latency at 100 targets | the performance table |

## 7. Proposed scope boundary for the specification

In: one Gateway, `CUSTOM_JWT` on tenant-identity, Policy from scopes,
native per-tenant limits, signed tenant context to Lambda tools, TVM in the
tool, per-tenant log lines and Contributor Insights, `ToolTarget` for
Lambda, OpenAPI, Smithy and MCP-server targets, one 3LO demo target,
cross-account Lambda as the extension.

Out: inference targets and model routing (own sample), semantic search as a
default, a RESPONSE interceptor as a default, per-tenant third-party static
keys at the Gateway (backend concern, shown once in a demo tool with
Secrets Manager `tenant/<id>/*` under the tenant credentials), Gateway per
tenant, cross-Region.
