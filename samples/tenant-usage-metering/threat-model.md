# Threat model

Status: written from the specification (`design/tenant-usage-metering.spec.md`)
before any code. Each mitigation points at the ADR or specification section
that defines it; when the sample is built, each specification reference is
joined by the code location, test or cdk-nag rule that implements it, and the
security review below is filled in.

Assets: the usage records a bill is built from, the tenants' raw usage
events, the registry of which cell may report for which tenant, the meter
and sink configuration, and the sink credentials.

Actors: the vendor (operators, usage readers, the control plane's global
hook, the metering service itself, administrators of the metering
account), emitters in vendor-owned and tenant-owned cell accounts, vendor
accounts that subscribe to the buses, and any other AWS account.

## Threats and mitigations

| Threat | Mitigation | Implemented by |
| --- | --- | --- |
| T-1: A caller forges its identity: names another emitter, cell, application or account in the event body | M-1: The ingest door is IAM-authorised; the function takes identity only from the verified assumed-role ARN and looks up `EMITTER#<account>#<role>`; body fields naming an emitter, cell, application or account are ignored, and the enriched fields are added by the function | ADR-0001; spec P-2, §3.2, §4.8 |
| T-2: A cell reports usage for a tenant it does not hold, in another cell, before or after it held it, or under another application's meter | M-2: Each event's `tenantId` must have a binding to the caller's cell whose `activeFrom`..`closedAt` (or one of its `intervals`) covers the event's `time`, else `TENANT_NOT_IN_CELL` or `REGISTRATION_CLOSED`; a meter with `allowedApplications` refuses other applications' emitters, `METER_NOT_ALLOWED`. Residual: registry reads are cached for 60 seconds, so a closed registration can admit events for up to a minute after it closes | ADR-0001; spec §3.2, §4.1, §4.2, §4.3, §5 |
| T-3: A tenant that controls a tenant-owned cell under-reports, or stops reporting, its own usage | Accepted: the sample proves who sent an event and which tenants it may speak for, not that the quantity is true. Production: bill only from emitters the vendor runs, or reconcile reported usage against cost or infrastructure signals the tenant cannot write | spec §1.2 |
| T-4: Code in a pooled cell reports usage for another tenant of the same cell | Accepted: a cell is vendor code and speaks for every tenant it holds. A role per deployment is a seam | spec §1.2; ADR-0001 Consequences |
| T-5: Any AWS account creates a role matching `<fleet>-ue-*` and floods the ingest door | M-5: The function refuses non-assumed-role and unregistered callers with a 403, stores nothing, and logs at most one line per caller per minute; reserved concurrency keeps the rest of the stack running; `POST /usage-events` has a method-level throttle below the stage limit and the admin routes their own, so a flood cannot fail the control plane's `PRE` hooks; an alarm fires on the unregistered-caller metric. Residual: a flood can still delay real emitters until the vendor blocks the source; AWS WAF rate rules are a production option | spec §3.2, P-8 |
| T-6: An account that holds cells reads other tenants' raw events or counted records from a bus | M-6: Both buses are shared through AWS RAM only with listed vendor accounts; `PutCellEmitter`, in the `CELL_CREATE` `PRE` hook, refuses a cell in a subscriber account or the metering account, and a deploy that adds an account already holding a cell fails. Residual, by design: a subscriber account sees every tenant's events, may subscribe unfiltered, and may replay the bus's retention; `UsageSubscriber` filters are a convenience | ADR-0006; spec §3.2, §3.4 |
| T-7: A principal other than the control plane registers an emitter or a binding, so a cell may report for tenants it was never given | M-7: Registration operations admit only `registrarPrincipalArns`, which a cell account neither holds nor trusts (the control plane's `<fleet>-global-hook`, control-plane R-41); synth refuses an ARN that is also an operator or reader. Residual: the registrar is only as strong as the control plane's hook-role boundary. Every global hook shares the role, and so does any principal that runs code as it: a control-plane operator, or a stolen operator token, through `PutHook`, and any principal with `codebuild:StartBuild` on the hook project or `states:StartExecution` on the workflow (control-plane T34, T41). Registrations carry the control plane's execution and operator ids, so one no execution explains can be found (M-22) | ADR-0001; spec §3.2, §3.3, §3.4 |
| T-8: A tenant-shaped value (`PARAM_BILLING_ACCOUNT`) runs as code in the hook, or reaches a billing system unchecked | M-8: The hook builds request bodies with `jq --arg` and never interpolates a value into a command line; `PutTenantBinding` refuses a billing account outside `[A-Za-z0-9._:-]{1,128}` | spec §3.4; control-plane §6.5 |
| T-9: A delete hook the control plane skips after its attempts leaves a registration `ACTIVE`, so the cell keeps reporting for a deleted tenant | Accepted: the control plane logs and alarms on every skipped hook (control-plane §8.3, T42); `ListTenantBindings` and `ListCellEmitters` let an operator compare and repair. Automatic reconciliation is a seam, left out to keep the sample's surface small | spec §1.1, §3.4 |
| T-10: Retries, redrives, re-admission or recounts count an event twice and inflate a bill | M-10: The recount keeps one event per `(applicationId, tenantId, eventId)` with a deterministic winner; the ingest bus also suppresses repeats within five minutes. Residual: an emitter that resends an event with a new `time` in another hour is counted twice; the emitter contract and snippet resend unchanged bytes | ADR-0003; spec P-5, §4.9, §6.1 |
| T-11: One application's emitter suppresses another application's events by reusing their `eventId`s | M-11: The dedupe key includes the `applicationId` of the verified emitter, so ids only collide within one application | ADR-0003; spec P-5 |
| T-12: An accepted event, a refusal that could still count, or a written usage record, is lost on the way, so a tenant is under-billed with no signal | M-12: The ingest subscriber retries for 24 hours into an SQS dead-letter queue with an alarm and `StartIngestRedrive`; ingest admits an event only while its hour has 49 hours of the recount window left; the object tracker's failures go to a replayed queue; the usage table is an outbox swept by the scheduler; a heartbeat alarm that does not depend on the scheduler fires if it stops; every bus reader built with `UsageSubscriber` has a dead-letter queue | ADR-0002, ADR-0006; spec §3.1, §3.5, §4.5, §4.7, §6.2 promises 7-8 |
| T-13: A total that a billing system already received changes under it | M-13: Totals are append-only by `seq`: a recount writes only the difference as an `ADJUSTMENT`. A record changes once at most, to add a missing `billingAccount` (revision 2). Each record has a stable `recordId` for idempotent delivery | ADR-0003; spec P-7, §4.7 |
| T-14: Two recounts of one hour race and write totals from a stale listing | M-14: A lease on the hour; every record write is a transaction with a `ConditionCheck` on the lease, and the final status write checks the hour's `generation`; the execution timeout is below the lease | spec §4.5 |
| T-15: An operator, by mistake or on purpose, changes a meter rule or a sink mapping and bills wrongly | M-15: Meter and sink operations admit only `operatorPrincipalArns`; meter versions are kept and apply from a named hour, so a revert stops the damage from the next hour. Residual: hours already counted under a bad version stay as counted (a backdated correcting version is a seam), and sink mappings keep no history | ADR-0004; spec §3.2, §4.1, §4.4 |
| T-16: An operator points a sink at a destination outside the vendor's control and sends usage there | M-16: `S3_EXPORT` writes only under a prefix of the sample's own export bucket, a separate bucket only the dispatcher may write. Accepted for `HTTP`: any HTTPS endpoint an operator configures is trusted, including, for a dispatcher in a VPC, private or link-local addresses (server-side request forgery). Production: an allowlist of endpoints set at deploy time, and refusal of private, loopback and link-local resolved addresses | spec §4.4 |
| T-17: A sink credential, or another secret, is sent to an endpoint the operator chose | M-17: A sink's `secretName` must sit under `<fleet>/metering/sinks/`, and the dispatcher's role may read only that prefix, so an operator cannot make the dispatcher read other secrets; an `AWS_IAM` sink carries no secret: the dispatcher signs each delivery with SigV4, only for an `https:` Lambda function URL or API Gateway host with no port, checked at create, on update and again before each send. The endpoint owner sees the role's access key id and session token, never its secret key; the signature is bound to that host, method, path and body and expires within minutes, so it cannot be reused elsewhere. The host check does not decide who owns the endpoint: what the dispatcher can invoke is bounded by the grants on its role, which the sample makes only for the demo receiver. Residual: a deployer who grants the dispatcher role invoke on `*` lets any operator POST mapped bodies to every function URL or API that grant covers, so grants name the billing endpoints only; no credential is logged | spec §3.5, §4.4, ADR-0007, [`src/shared/sink-auth.ts`](src/shared/sink-auth.ts) |
| T-18: The wrong tenant account is billed, or a record's billing account changes after it was sent | M-18: `billingAccount` is copied onto each record once, from the tenant's binding for that application, and never changed after; a missing one blocks only the sinks that need it, with an alarm and a release path. Residual: the value comes from `PARAM_BILLING_ACCOUNT` as the control plane delivers it, so a value that names another tenant's billing account is trusted; production: the billing system checks the mapping from tenant to billing account, or the value comes from a vendor-only source | spec §3.4, §4.7 |
| T-19: Usage events carry personal data that should not sit in a billing store | Accepted for the sample: events hold ids, meters, values and up to ten dimensions of synthetic data. Emitters keep personal data out of `dimensions`, which travel to the raw and error stores, both buses' subscriber accounts and every sink. Retention: lifecycle expires raw objects after `rawRetentionDays` and error objects after `errorRetentionDays`, and noncurrent versions 7 days later | spec §3.3, §3.5, §4.8, §6.1 |
| T-20: Usage data at rest is encrypted under keys the vendor does not control | Accepted, for the sample's simplicity and cost: S3, DynamoDB, SQS, Firehose and the buses use their default encryption at rest; the defaults of the new Custom Event Bus are to be checked at build. A customer-managed key per store is a production option | accepted |
| T-21: A late or redriven event lands after its hour closed and is silently uncounted | M-21: Ingest's accept window, a close guard checked at each write of `READMIT`, `RECOUNT` and `INGEST_REDRIVE` (refused items go to `error/` as `TOO_LATE`), a close that checks the hour's `generation`, and an alarm on any object in a `CLOSED` hour. Residual: such an object stays uncounted; the alarm is the signal and no remediation runs | spec §3.3, §4.5, §4.6 |
| T-22: Operator, registrar and job actions cannot be traced to who did them | M-22: API Gateway access logs on every route with the caller ARN and request id, kept for `rawRetentionDays`; `createdBy` and `createdAt` on meter versions, sinks, registrations and jobs; registrations also store the control plane's execution and operator ids | spec §3.4, §3.5 |
| T-23: A registered emitter, for example a tenant-owned cell, floods the ingest door or one hour | M-23: A per-emitter admission limit (`maxEventsPerEmitterPerMinute`, default 3,000, over it `RETRY`) and a per-emitter cap, with an alarm, on stored refusals that can never count; refusals that could still count are always stored. Residual: about 20 emitters at their limit fill the account's sustained ingest, and the others get `RETRY`; the hour is a fleet-wide unit, so an emitter that fills an hour under its limit slows every tenant's count of it; the distributed map is a seam | ADR-0003; spec §3.2, §3.3 |
| T-24: A principal in the metering account writes into the pipeline past the ingest checks: raw, re-admitted or error objects, the ingest dead-letter queue, the ingest bus, the Firehose stream, registry, meter or sink items in the table, or forged `UsageRecorded` events on the usage bus | M-24: Explicit-deny resource policies with `aws:PrincipalArn` conditions, which an identity-policy allow does not get around: each bucket prefix only by its pipeline role, deletes, lifecycle, versioning, policy and notification changes denied, versioning on; the dead-letter queue only from the ingest subscriber; the ingest bus only from the ingest function; the usage bus only from the record publisher; table item writes, PartiQL included, only from the stack's own roles. Residual: Firehose has no resource policy, so a principal granted `firehose:PutRecord*` on the stream can write raw usage (production: an SCP or permissions boundary); any principal allowed to change the queue, bus or table policies, to run the deployment or provider roles, to invoke the auto-delete-objects or bucket-notifications provider functions, or to delete the stack can undo these controls and is trusted, as is an administrator of the metering account; Object Lock, which also removes the auto-delete-objects provider, is a production option | spec §3.5 |
| T-25: The hook sends its signed registrar request to a host the tenant chose, which replays it within the signature's lifetime | M-25: The hook reads the admin API URL from `metering-hook.env` in its own source, never from a `PARAM_` value, which deployment events take from the tenant-shaped deployment set | spec §3.4; control-plane R-32, R-42 |
| T-26: A resource in another account drives a service role or queue of the stack (confused deputy) | M-26: Every service-principal trust policy and resource policy (the S3 notification permission, queue policies, Scheduler, Firehose and subscriber role trust) is conditioned on `aws:SourceArn` and `aws:SourceAccount`; the DynamoDB Streams trigger uses the function's own role | spec §3.5 |
| T-27: Usage data or credentials end up in logs, execution history or the error store for longer than needed | M-27: No event payload, sink body or credential is logged; recounter state holds keys and counts only; error objects, and their noncurrent versions, expire after `errorRetentionDays` (default 30, at least the recount window in days plus 7) and 7 days more | spec §3.3, §3.5 |

## Security review

Run on 2026-11-18 on the synthesised tree (`npx cdk synth` with the test
account and Region): ProtoShield v0.18 (MIT-0 license-header config in
`.protoshield/config.yaml`) and ASH in local mode. cdk-nag
`AwsSolutionsChecks` runs in every synth and passes; every suppression
carries a reason in code. No critical finding.

| Finding | Scanner | Disposition |
|---|---|---|
| Demo operator and reader roles allowed `execute-api:Invoke` on every route | ProtoShield, high | Fixed: each stand-in role is granted only its routes from `src/api/routes.ts`; the API resource policy denies the rest anyway |
| Dispatcher may read every secret under `<fleet>/metering/sinks/` | ProtoShield, high | Accepted: sinks are run-time configuration (ADR-0004), so their secrets are not known at deploy time; the prefix is the boundary, and `CreateSink`/`UpdateSink` refuse a name outside it (spec §4.4) |
| `grantReadWriteData` on the admin and jobs roles | ProtoShield, medium | Accepted: the admin API writes every item kind (meters, sinks, registrations, jobs) and `SINK_REDRIVE` scans; the table policy still limits writers to the stack's roles |
| Firehose bucket-level `ListBucket`, `GetBucketLocation` | ProtoShield, medium | Accepted: Firehose's S3 destination needs them on the bucket (the delivery role's documented permissions) |
| `minimatch`, `glob` CVEs (denial of service) | ProtoShield, medium | Accepted: development dependencies of jest and eslint, on `main` across the repository; nothing in a bundled function uses them |
| Test fixtures `user:pw@billing.example.com`, `secretName` values | ASH detect-secrets | False positive: the strings are refusal cases in `test/pure.test.ts` and `test/integ.metering.ts` |
| Log groups not KMS-encrypted; SQS queues with SQS-managed SSE, not KMS | ASH checkov | Accepted: logs carry no payload or credential (spec §3.5); SSE-SQS encrypts at rest; a customer key is a production option |
| Lambda: no DLQ, not in a VPC, no reserved concurrency, environment not KMS-encrypted | ASH checkov | Accepted: async invocations have on-failure destinations where they matter (tracker, jobs are re-runnable); the functions reach only AWS APIs and the configured sinks; only the ingest function needs reserved concurrency (spec §3.2); the environment holds names, no secret |
| Access-log bucket without its own logging and versioning; API without caching or X-Ray | ASH checkov | Accepted: logging the log bucket to itself would loop; caching would serve stale usage; tracing is production hardening |
| Findings under `cdk.out/`, `node_modules/` and `src/smithy/` | ASH | Not the sample's source: generated output, gitignored |
| Lambda function URL in the demo stack | Design | Fixed (was `AuthType NONE` with a resource policy open to any principal): `integHttpReceiver=true` (off by default) adds a stand-in billing API behind an `AWS_IAM` function URL. Only the dispatcher's role is granted invoke, as an identity grant, so the function has no resource policy; an unsigned call is refused by Lambda (403, checked by the integration test before use). It stores nothing, has reserved concurrency 2, and is deleted with the stack. Never part of the construct |
