# Threat model

Status: design only. Nothing is built, so every "Planned:" entry names a
test, step or check that does not exist yet. Unit test file names are
proposals. Integration step names are the ones in spec §8. Claims marked
with an `S-n` come from the 2026-11-18 and 2026-11-19 spikes, S-1 to S-15 (spec §7), not
from the built sample.

Scope and assumptions:

- The attacker is code that runs in a sandbox (written by a tenant, or by
  an agent acting for one) and a tenant that calls the tool.
- The vendor's components are trusted: the tool, the reaper, the drain, the
  offboard function, the consumed ingress on the gateway entry, and the
  vendor's own API on the standalone entry. The ingress authenticates the
  tenant and signs the tenant context (agentic-runtime-isolation); the
  vendor's API verifies its own identity provider's token (ADR-0017).
- The hypervisor of each AWS boundary (Lambda MicroVM, Nitro Sandbox,
  AgentCore session) is the wall between tenants; the sample does not
  re-test it.
- "Enforced" means IAM refuses the call even when the tool's code is wrong.
  "Filtered" means the tool's code decides and IAM has no key for it
  (spec §3.4, P-6).

## Cross-tenant execution

| Threat | Mitigation | Implemented by |
| --- | --- | --- |
| T-1: Tenant A's call lands in tenant B's `nitro` task because ECS gave B's task A's old private IP | M-1: Per-start 32-byte nonce; the task holds only its hash from the start call. The tool sends the nonce in a TLS `/hello`, and the honest runner of another task refuses it because the hash does not match, before any job byte. The answer `HMAC(nonce, challenge ‖ certFingerprint)` ties the job to the connection's certificate. A failure marks the row dead and starts a fresh task. S-7 saw no IP reuse (not ruled out); the check does not depend on it | ADR-0010; spec §3.4 Identity check; Planned: integ `recycled-address`; `runner/test_runner.py` "hello refuses a challenge answered with another nonce" |
| T-2: A MicroVM or AgentCore session is not the one the row names (handle replaced, session restarted under the same id) | M-2: Every job carries `jobAuth`, and a runner whose hash or session does not match refuses before any code runs (M-51); the result's `HMAC(nonce, runId)` confirms the peer accepted. A changed `bootId` means a restart: the row is rewritten and the call reports `sandbox` = `started`. A failed check, "not found" or a refused connection marks the row dead, and the address is never retried | ADR-0010; spec §3.4, §4.1 step 3; Planned: integ `dead-handle`, `reuse`, `apart`; `test/tool.test.ts` "dead handle takes over with the version just read" |
| T-3: Two concurrent first calls start two sandboxes for one tenant, or a call takes over a start another call still owns | M-3: Conditional put on `attribute_not_exists(PK) OR version = :seen` gives one winner. The start lease equals the start cap. `clientToken` is the first 32 hex of SHA-256("start" ‖ nonce), so a retried start launches nothing new. The loser returns `sandbox_starting`. Each write uses the version of the call's own last write | ADR-0005; spec §4.1; Planned: `test/registry.test.ts` "one winner under concurrent takeover"; integ `race`, `cold-from-zero` |
| T-4: A sandbox is shared or handed from one tenant to another | M-4: One row per tenant per backend, key `TENANT#<t>` / `SANDBOX#<backend>`, read with the tenant-scoped role. A replaced handle is stopped before the new start. No sandbox is started per call or reused across tenants | P-4; ADR-0005; spec §4.1, C-1; Planned: integ `apart` |
| T-5: Session-id guessing on `agentcore`: anyone who knows a tenant id can compute its session id | Accepted: the id is `rc-` + hex SHA-256 of the tenant id, so it is derivable. Knowing it adds no reach, because only the tool role may invoke the runtime and the tool takes the tenant from a verified identity (M-38). M-5: `InvokeAgentRuntime` is granted to the tool role only (one role, shared by every tool function), `StopRuntimeSession` to the tool and reaper roles only | ADR-0009; spec §3.4, §3.6; Planned: `test/backends.test.ts` "session id is 67 characters, `rc-` plus 64 hex"; `test/construct.test.ts` "only the tool role may invoke the runtime" |
| T-6: A defect in the tool's code starts, calls or stops another tenant's MicroVM or AgentCore session (filtered start and call) | Accepted: IAM cannot stop it. MicroVM actions authorize against the image only (S-3), and AgentCore invoke and stop have no session-id key (S-8). Compensating: the tenant comes only from the signed context (M-38), and the session id comes from the tenant alone (M-5). M-51: every job carries `jobAuth`, bound to the sandbox's nonce, and an honest runner refuses a job it may not adopt (hash mismatch on `microvm` and `nitro`, session-id mismatch on `agentcore`) before it writes the input or starts code, so a wrong target runs nothing; on `nitro` the `/hello` check also comes before any job byte. Assumes the vendor runner is the sole listener (spec §3.5) | P-6; ADR-0009, ADR-0014 consequences, ADR-0018; spec §3.4 enforced or filtered rows and Identity check; Planned: `runner/test_runner.py` "job with another nonce's `jobAuth` is refused and writes nothing", "`agentcore` job whose `tenantId` does not hash to the session id is refused, on a fresh and on an adopted session"; `test/tool.test.ts` "a `wrong_sandbox` refusal marks the row dead"; integ `recycled-address`; revisit when AWS adds MicroVM tags or an AgentCore session key (ADR-0015) |

## Cross-tenant data access

| Threat | Mitigation | Implemented by |
| --- | --- | --- |

IAM refuses any other key | ADR-0005, ADR-0006; spec §3.6, C-5; Planned: integ `iam-wall` (simulated denial of `inputs/B/*`, row `TENANT#B`); `test/construct.test.ts` "tool role has no s3 or dynamodb data action" |

Enforced | ADR-0014; spec §3.6; Planned: `test/construct.test.ts` "every condition key is supported by its action"; integ `iam-wall` (`StopTask` on B's task) |
| T-9: A call starts a task from another definition, another cluster, or with a role passed in | M-8: `RunTask` is allowed on the pinned task definition revision ARN only. | T-10: The `input` name reaches outside the caller's prefix (traversal, absolute path, long name) | M-9: Name matches `[A-Za-z0-9._/-]{1,256}`, no `..`, no leading `/`; the key is built as `inputs/<tenantId>/<name>` from the verified tenant. | T-11: Code in one `agentcore` session reads or writes another session's files (`sessionFiles` on) | M-10: Off by default. | T-13: Users of one tenant share a sandbox: one user's code reads files another user's code left in `/work` | Accepted: R-4 is one sandbox per tenant, not per user. Jobs run one at a time and `/work` persists for the sandbox's life, so the next turn can read the last | ADR-0009 Option 3; spec §3.5; per-user sandboxes are a later option |

## Runner compromise

| Threat | Mitigation | Implemented by |
| --- | --- | --- |
| T-40: Code kills or replaces the runner, or forks a child that outlives the timeout (`setsid`, kill of PID 1) | M-24: Code runs as uid 1001 in a new session and process group. At `runTimeout` or job end the runner kills the group and then every uid 1001 process. uid 1001 cannot signal the runner, open its descriptors, or write outside `/work` and `/tmp`. The tool's own timeout stops the sandbox if the runner stops answering | ADR-0010; spec §3.5, C-4; S-4, S-5, S-10; Planned: integ `runaway`; `runner/test_runner.py` "kill reaps a `setsid` child" |
| T-41: Code posts its own `/run` hook to port 9000 to set the nonce hash first (`microvm`) | M-25: No tenant code runs before the hook delivers the `nonceHash`. Until then `/ping` shows no `bootId` and the job route refuses. The 9000 listener accepts the hook once and serves no jobs. Tool tokens allow 8080 only | spec §3.5; S-2; Planned: `runner/test_runner.py` "second `/run` hook is ignored", "job refused before the hook" |
| T-42: Values made at process start are shared by every sandbox restored from one snapshot (`microvm`, `agentcore`), so a nonce or `bootId` repeats | M-26: The runner makes `bootId` when the sandbox first serves a tenant (the `/run` hook, the session's first job), takes its `nonceHash` where there is one (`microvm`, `nitro`), and adopts the nonce only on the data channel. Every random value comes from `os.urandom` or `secrets`. On `nitro` the key pair is made in memory at process start | ADR-0010 and ADR-0015 notes; spec §3.5; S-10; Planned: `runner/test_runner.py` "`bootId` differs between two restores" |
| T-43: A caller, or a tool defect, reaches an `agentcore` session first and plants another tenant's nonce, which the runner adopts | M-27: Only the tool role may invoke the runtime (M-5). The runner adopts a nonce only when the invocation's session id equals `rc-` + SHA-256 of the job's `tenantId`, which `jobAuth` covers, so another tenant's job is refused. A refusal marks the handle dead. `bootId`, not the nonce, shows a restart | ADR-0010; spec §3.4 Identity check; Planned: `runner/test_runner.py` "`agentcore` job whose `tenantId` does not hash to the session id is refused, on a fresh and on an adopted session"; `test/tool.test.ts` "a `wrong_sandbox` refusal marks the row dead" |
| T-44: Code forges a run record or an operator's view of one | M-28: The tool's log line is the record of a run and is written by the tool Lambda, not the sandbox. | T-45: Code prints forged lines into the task or runtime log stream the runner shares on `nitro` and `agentcore` | Accepted: the lines are the tenant's own output and can only mislead an operator who reads the runner log. The tool line is the record, and the runner log is secondary | spec §3.5 |
| T-46: Code gains root in its VM or escapes it | Accepted: the VM is the boundary (P-3). With root the code still sees only its own tenant's bytes. A hypervisor flaw is AWS's to fix | ADR-0010; spec §1 |

## Resource exhaustion

| Threat | Mitigation | Implemented by |
| --- | --- | --- |
| T-48: A runaway job (loop, sleep) holds the sandbox | M-29: Three caps. The runner kills the group at `runTimeout` (`RLIMIT_CPU` too). The tool stops the sandbox at `runTimeout` + 5 s and returns `timedOut`. The platform or reaper ends the sandbox at `sandboxMaxLife`. Synth bounds `runTimeout` to 1 s to 60 s and sets the tool timeout to cover them | P-7; ADR-0010; spec §3.3, §3.5, §4.1 step 5, C-4; Planned: integ `runaway`, `max-life`; `test/construct.test.ts` "tool timeout equals the budget" |
| T-49: A fork bomb | M-30: `RLIMIT_NPROC` = N for uid 1001, processes and threads, soft = hard, set before the uid drop (10 at the default `microvm` size, 64 on `nitro` and `agentcore`); the group kill and the uid sweep end every child | ADR-0010, ADR-0019; spec §3.5; Planned: integ `runaway`; `runner/test_runner.py` "process limit is applied" |
| T-50: Code fills memory | M-31: `RLIMIT_AS` and `RLIMIT_NPROC` per backend (spec §3.5 memory cap), set with soft = hard before the uid drop so code cannot raise them (S-15), and the sandbox's own memory is the outer bound | spec §3.5; ADR-0019; Planned: `runner/test_runner.py` "address-space limit is applied" |
| T-51: An out-of-memory kill takes the runner down (`RLIMIT_AS` is per process, not a total) | M-53: each backend caps the job's total (spec §3.5 memory cap). `microvm`: `RLIMIT_AS` × `RLIMIT_NPROC` stays at or below 70 % of the guest, so an allocation fails inside the job and the kernel killer is not reached (S-15). `nitro`: the platform's task limit and the 200 ms watchdog; the kernel killed only jobs and the runner survived (S-14). `agentcore`: a cgroup per job with `memory.oom.group` = 1, after the runner has written 0 to the root's `memory.oom.group`, without which one kill ends the session (S-14). The design relies on no `oom_score_adj` value on `microvm` and `agentcore`; on `nitro` runner survival was measured at the platform's -998, with the watchdog as cover. The runner deletes uid 1001's files under `/tmp` and `/dev/shm` after each job, and on `microvm` also makes both unwritable to uid 1001; on `agentcore` one job group lasts the session, so leftovers count against the next job. S-16: `/work` is disk on every backend; on `nitro` an unmapped `memfd` or a `/dev/shm` file is not seen by the watchdog and is killed by the kernel only at the task limit, runner alive; on `agentcore` the job group kills it at L. On `microvm` see T-84. If the runner still dies, the damage stays in the tenant's own sandbox and the tool replaces it | ADR-0019; spec §3.5; S-14, S-15; Planned: integ `runaway` (the job and N − 1 children at their `RLIMIT_AS`); `runner/test_runner.py` "watchdog kills a group over its total", "rlimits are set with soft = hard before the uid drop", "`agentcore` setup moves the runner into `/runner` before `+memory` and writes 0 to the root `memory.oom.group`", "`agentcore` job group has `memory.max` = L and `memory.oom.group` = 1 and is reused", "`microvm` N is ⌊0.7 × `MemTotal` / 256 MiB⌋ and A stays 256 MiB for any size", "`nitro` M is the smaller of `MemTotal` and the task group's `memory.max`", "`nitro` sets `memoryExceeded` when `oom_kill` grows", "watchdog runs on `nitro` only", "on `microvm` `/tmp` and `/dev/shm` are not writable by uid 1001", "step 3 deletes uid 1001's files under `/tmp` and `/dev/shm`"; S-16, S-17 |
| T-84: `microvm` code fills memory that no rlimit counts (an unmapped `memfd`, socket buffers, SysV semaphores and queues, `vmsplice` pages, a tmpfs in a user namespace), and the guest runs out: the kernel kills the runner and the MicroVM ends, with no result and no cause (S-16: 3840 MiB of `memfd` in about 1 s, 3 of 3) | M-54: the runner installs a seccomp filter in every `microvm` job after the uid drop that returns `EPERM` for each of those routes and for mounts, `unshare` and socket buffer sizing, and checks `Seccomp: 2` before it sends the input; the job cannot remove it (S-17). Routes left open add at most about 430 MiB. A free-memory floor (`MemAvailable` below 512 MiB, every 200 ms) kills the job as a backstop. Residual: a route the list misses that fills faster than the floor polls; the floor is untested.
