# Runtime Isolation — Threat Model

> Status: **Implemented and verified 2026-10-27.** 38 threats (T-1 to T-38),
> 28 mitigations (M-1 to M-28). First written 2026-10-26 from
> [`design/runtime-isolation.spec.md`](./design/runtime-isolation.spec.md)
> (P-1 to P-9, §3.4, §6, and the §7.1 spike results V-1 to V-7) and ADR-0001
> to ADR-0013, enumerated STRIDE-per-boundary with the threat-modelling MCP
> server (Threat Composer export kept out of the repository). Extended
> 2026-10-27 for the scale fixes: T-35 to T-38 and M-25 to M-28 (ADR-0020 to
> ADR-0022). Every mitigation points at the principle or ADR that motivates
> it and at the code that implements it. The last integration run and the
> security scans were on 2026-10-27; the dispositions are in
> [Security review](#security-review).

Scope: the `IsolatedRuntime` construct with its one backend (AgentCore
Runtime) and either ingress (API Gateway REST with Lambda, or AgentCore
Gateway with a REQUEST interceptor), the always-on token vending machine and
the three optional modules (session mapping, scope checks, delegation), the
demo stack, and the published
and consumed SSM parameters. Out of scope: how the identity provider issues
and narrows tokens ([tenant-identity's threat model](../tenant-identity/threat-model.md)
covers that), what the vended credentials unlock beyond the demo table
(data-layer samples), and the Runtime's own microVM implementation (AWS
shared responsibility; T-24).

## Actors

| Actor | Trust | What they hold |
|---|---|---|
| Tenant user | authenticated, one tenant | an access token with `tenant_id`, `sub`, `client_id`, `scope` |
| Malicious tenant user (same or another tenant) | authenticated | a valid token for tenant B or user A2, and a will to reach A1's unit, data or credentials |
| Internet caller | none | forged, expired or replayed tokens; load |
| Other IAM principal in the vendor account | elevated | an identity policy that allows `bedrock-agentcore:InvokeAgentRuntime`, `ssm:PutParameter`, or CloudWatch Logs reads |
| Vendor deployer | administrative | instantiates the construct; owns `tvm.role`, the SSM parameters and the cdk-nag suppressions; can misconfigure |
| The agent itself | caller-influenced | code inside the microVM: the MMDS execution-role credential (logs/traces only), the vended tenant credentials (always present, used for the model call and data), and on opt-in the forwarded user token; a prompt injection or dependency compromise acts with all three, but none reaches another tenant or a shared model |

## Assets and trust boundaries

| Asset | Why it matters |
|---|---|
| Tenant user access token (A-1) | The only source of tenant context (P-3); forwarded to the agent on opt-in (P-5) |
| Unit id, `runtimeSessionId` (A-2) | Names the microVM. Not a secret: the ingress principal, not the id, is the credential (ADR-0002) |
| Tenant-scoped STS credentials (A-3) | 15 to 60 minutes of `TenantId`-tagged access, used for the model call and any tenant data; always in transit through the ingress and the Runtime in a header (ADR-0012, ADR-0018) |
| Execution-role credential, MMDS (A-4) | Readable by any code in the microVM, but grants only logs and traces — no model, no data (ADR-0008 amended by ADR-0018) |
| Ingress role credential (A-5) | The one principal the Runtime trusts; with TVM, the one principal the tenant role trusts |
| Conversation state inside a microVM (A-6) | One tenant user's prompts, model output and memory |
| Tenant data behind the TVM (A-7) | The demo table's `TENANT#<tenantId>` items; whatever a consumer puts behind the same credentials |
| Consumed and published SSM parameters (A-8) | Decide which issuer the ingress trusts and where consumers send tenant tokens |
| Telemetry (A-9) | Must carry `tenantId`, never a token or a credential (P-9) |

| Boundary | Crossed by | Authenticated by | Layer (`ARCHITECTURE.md` §3.3) |
|---|---|---|---|
| B1 Client → ingress | `POST /invocations` with a bearer token | the ingress verifier (M-1) | Identity |
| B2 Ingress → Runtime; anyone else → Runtime | `InvokeAgentRuntime` | SigV4 and the Runtime resource policy (M-2); the ingress alone sets the unit id (M-3) | Invocation, Session |
| B3 Runtime → microVM | the session id selects the VM; allowlisted headers are delivered | the service; a data-free execution role (M-7, M-8); `requireMMDSV2` is not exposed by `AWS::BedrockAgentCore::Runtime` in aws-cdk-lib 2.274.0, so it is a follow-up (T-13) | Session |
| B4 Ingress → tenant role; agent → tenant data | `AssumeRole`+`TagSession`; data calls with the vended credentials | the tenant role's trust policy and ABAC on `${aws:PrincipalTag/TenantId}` (M-10, M-11, M-15) | Data, Delegation |
| B5 Everything → telemetry and parameters | logs, metrics, `ssm:GetParameter`/`PutParameter` | IAM; field-allowlisted loggers (M-12, M-18, M-20) | Observability |

## Threats

| ID | Threat | Consequence | Status | Mitigations |
|---|---|---|---|---|
| T-1 | A forged, expired, or ID token, or one signed by an unknown key, is presented as a tenant user (B1) | Acting as a tenant user without a sign-in | Mitigated by design | M-1, M-6 |
| T-2 | A valid token from another app client or another issuer (any Cognito pool in the Region, a vendor-side token) reaches the ingress | Tokens the vendor never meant for the agent are accepted | Mitigated by design: `iss` is pinned to `identity.discoveryUrl`, `client_id` to `identity.allowedClientIds` | M-1 |
| T-3 | A token naming several tenants (a `tenants` claim) or none at all reaches the ingress | The unit, the session tags and the data scope chosen for a tenant the user did not intend, or for no tenant | Mitigated by design; single-tenant users only (spec §1.2, §6.2) | M-1 |
| T-4 | A stolen access token is replayed against the ingress until it expires | The thief opens or resumes that user's conversations as that user, for up to 5 minutes (tenant-identity N-1) | **Accepted**: the token *is* the user for its lifetime. It reaches only that user's own units and data, never another tenant's (M-2, M-3); any vended credential expires with `tvm.durationSeconds` (M-14). Client-side token hygiene and revocation are outside the sample | M-2, M-3, M-14 |
| T-5 | Another IAM principal in the account whose identity policy allows `InvokeAgentRuntime` calls the Runtime directly with any `runtimeSessionId`, bypassing the ingress (V-1) | Any tenant's session reachable without a token; filtered isolation collapses | Mitigated by design; V-1 PASS: an Admin role and a same-account role with an identity-policy allow both get an explicit deny from the resource policy | M-2, M-22 |
| T-6 | A cross-account principal, or any caller using `InvokeAgentRuntimeForUser`, the WebSocket or the `InvokeAgentRuntimeCommand*` variants, reaches the Runtime or its endpoint | A second path into tenant sessions beside the ingress | Mitigated by design: cross-account needs a resource-policy allow that does not exist; the other variants are denied to `*`; V-1 showed the endpoint needs no policy of its own | M-2 |
| T-7 | Tenant B or user A2, holding a valid token, sends A1's unit id in `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id` or in the body (ADR-0002, V-3) | Landing in A1's microVM and reading its conversation state | Mitigated by design: the ingress derives the id from the verified claims and ignores (API Gateway) or overwrites (Gateway, V-3) the client's value; residual on the Gateway path is T-11 | M-3, M-2, M-5 |
| T-8 | With session mapping on, two users pick the same `conversationId` (collision, copy or guess) | Two users sharing one unit if the id alone selected it | Mitigated by design: the prefix `sha256(tenant_id\|sub)` qualifies the id per user; the spike saw A2 with A1's `conversationId` land in a different microVM | M-3 |
| T-9 | A `conversationId` sent while session mapping is off, a malformed `conversationId`, or a non-string `prompt` | An accidental shared unit, a Runtime error that leaks internals, or agent input confusion | Mitigated by design | M-3, M-16 |
| T-10 | A token lacking a scope the deployer requires invokes the agent | The deployer's scope-based access control not applying (ADR-0005) | Mitigated when `requiredScopes` is set; off by default (P-4) | M-4 |
| T-11 | The Gateway REQUEST interceptor errors, times out, is throttled, or is detached, and the Gateway forwards the request with the client's own session header | On `agentcore-gateway`, the unit choice (P-2) and the delegation and TVM checks skipped: fail-open | **Accepted**: in-code failures short-circuit to 403 (the Gateway returns a `transformedGatewayResponse` without calling the target). The Gateway's behaviour on an *uncaught* interceptor failure is not documented and was not spiked, so `agentcore-gateway` carries the larger residual and the README says so. Alarm on interceptor errors and throttles. **Follow-up**: an integ probe that throttles the interceptor (reserved concurrency 0) and asserts the Runtime is not invoked; `scripts/integ.sh` has no such step yet | M-5, M-2, M-22 |
| T-12 | On API Gateway, a cached authoriser result is reused for a different token, or a method exists without the authoriser | A request passing the integration Lambda with stale or absent claims | Mitigated by ADR-0015 (cache length amended by ADR-0023): the authoriser result cache is 300 s and keyed on the whole `Authorization` header, so a cached Allow applies only to the same token and is at most 300 s stale; the integration Lambda re-verifies the token, including `exp`, before any invoke; one method; claims read only from the authoriser context | M-6, M-1 |
| T-13 | Code in the microVM (prompt injection, dependency compromise, tool bug) reads the execution-role credential from MMDS and uses it (ADR-0008) | Whatever the execution role can reach is reachable by caller-influenced code | Mitigated by design: since ADR-0018 the role can write logs and traces only — no model and nothing tenant-scoped (P-6). The model is reachable only with the vended per-tenant credentials, so a stolen execution-role credential cannot even run up model cost | M-7, M-15 |
| T-14 | With `forwardUserToken` on, the agent logs, echoes or exfiltrates the forwarded bearer token; with it off, a client injects the custom user-token header (ADR-0006) | A tenant user's bearer token leaving the microVM, or a client planting a token the agent trusts | **Accepted** for the on case: the agent holds a live 5-minute token, as the delegation pattern intends (the Runtime is the trusted boundary). The header is allowlisted only when on, client-supplied custom headers are stripped, and the agent redacts; the residual is the agent's own code | M-8, M-12 |
| T-15 | With forwarding on, an un-narrowed token (`tenant-api/read tenant-api/write`, `aws.cognito.signin.user.admin`) is forwarded (ADR-0007) | The agent can call tenant-identity's tenant API or Cognito user APIs as the user: more delegated authority than the task needs | Mitigated when `requireNarrowedToken` is set; without it the deployer chose to forward the full token and the README says so | M-9, M-8 |
| T-16 | The deployer's `tvm.role` trust policy trusts more than `tvmCallerRole`, omits the `TenantId` request-tag condition, or leaves `aws:TagKeys` open (ADR-0012) | Any principal that can call `sts:AssumeRole` reads every tenant's data | **Accepted, deployer-side**: the construct grants only its half (the ingress role's `AssumeRole`/`TagSession` on `tvm.role`) and cannot validate a role it does not own. The contract is spec §6.1, the demo ships a correct role, integ step 8a proves the runner is refused, and the hardening checklist names the review. **Riskiest deployer-side item** | M-10, M-22 |
| T-17 | Tag injection through `tvm.claimTags`: a mapped claim the user influences, or a `claimTags` key of `TenantId` or `UserId` | ABAC conditions keyed on the injected tag granting another tenant's data | Mitigated by design: reserved keys fail synth; values come only from the verified payload; a missing claim is 403; the deployer is told to map only claims the identity provider sets from vendor data | M-11, M-10 |
| T-18 | A hop on the path logs request header values (API Gateway data trace or access-log format, interceptor log, Runtime or OTEL streams), recording the credential or user-token header (V-7) | Live tenant-scoped STS credentials, or a bearer token, in a log for anyone with Logs read | Mitigated by design and verified: the V-7 sweep found zero hits for `ASIA`, `secretAccessKey`, the base64 credential prefix, the header name and a JWT prefix across every log group. `dataTraceEnabled` MUST stay off; the agent and OTEL MUST not record headers. Residual: a later deployer change; unit tests pin the stage settings | M-12, M-8 |
| T-19 | A tenant is offboarded or a user disabled while vended credentials are still valid in the microVM or the ingress cache | Data access continues for up to `tvm.durationSeconds` after the identity provider stopped issuing tokens | **Accepted**: STS credentials cannot be recalled before expiry short of a deny on the role. New vends stop at once because the token is re-verified per request; the window is 15 minutes by default, 1 hour at most. An offboarding runbook that attaches a `TenantId` deny to the tenant role is a deployer action | M-14, M-13 |
| T-20 | The credential cache serves credentials vended for a different tag set (key incomplete when `UserId` or `claimTags` are on, or an entry mutated after insertion) | Cross-tenant or cross-user credentials from the ingress | Mitigated by design: the key is the canonical full tag set plus role ARN | M-13, M-11 |
| T-21 | Many distinct tenants or users, or forced cache misses (cold starts, many Lambda environments), drive `sts:AssumeRole` past the account's STS limit | Every tenant's TVM path fails with throttling: denial of service through the TVM | **Accepted**: the cache keeps STS at about one call per tenant (or user) per lifetime per Lambda environment (V-7: one `AssumeRole` per tenant, not per request), but STS limits are per account and shared, and `includeUserIdTag` multiplies the key space. Narrowed by T-36 (ADR-0022) | M-13, M-19, M-26 |
| T-22 | Prompt injection persuades the agent to read `TENANT#<other>` or to name another tenant in a tool call | Another tenant's data in the response, if code rather than IAM were the wall | Mitigated by design: the agent only holds credentials tagged with the caller's `TenantId`, has no `sts:AssumeRole` of its own, and the cross-tenant read fails in IAM (V-7: `AccessDeniedException` from DynamoDB). Prompt injection can waste tokens, not cross tenants | M-15, M-10, M-7 |
| T-23 | With `session.scope: 'tenant'`, any user of the tenant resumes a conversation another user of the same tenant started | Users within one tenant reading each other's conversations | **Accepted by design**: that scope trades user separation inside a tenant for fewer cold starts (ADR-0002); off by default (`'user'`); the README states it | M-3 |
| T-24 | The Runtime fails to isolate or sanitise a microVM | A cross-session leak below the sample's control | **Accepted**: service boundary (shared responsibility). The sample gives the agent a data-free role so a breach gains nothing tenant-scoped (`requireMMDSV2` is not yet exposed by the CloudFormation resource, a T-13 follow-up); everything tenant-scoped the agent holds expires with the token or the credential | M-7 |
| T-25 | An agent answer outruns an intermediate hop's timeout, or many long streams are opened (V-4, V-5) | Truncated answers reported as success; the API Gateway integration Lambda held for the whole stream | Mitigated: timeouts aligned end to end (V-5: 29 s cut the stream, 2 min did not); the cost of long streams on API Gateway is measured and reported (ADR-0009) | M-17, M-19 |
| T-26 | One tenant's script saturates the shared Runtime, the Lambda concurrency or the Bedrock model quota | Every other tenant throttled: a noisy neighbour in the pool model | **Accepted**: API Gateway has a stage throttle and can take WAF and per-tenant usage plans (tenant-identity ADR-0025 is the worked example); `agentcore-gateway` has no per-tenant throttle in this sample and the Gateway's and Runtime's quotas apply to all tenants together. Hardening checklist item. Narrowed by T-35 (ADR-0020) | M-19, M-18, M-25 |
| T-27 | Raw tokens, prompts or tenant identifiers written to logs as free text | Logs become a credential or conversation store | Mitigated by design | M-12, M-18 |
| T-28 | The session prefix in Runtime log stream names and ingress logs is inverted to `tenant_id` and `sub` | Pseudonymous identifiers resolving to users | **Accepted**: the prefix is a truncated SHA-256, logged next to `tenantId` at the ingress on purpose so a session joins back to a tenant (P-9). `tenant_id` is an opaque ULID and `sub` an opaque Cognito id, not personal data | M-24 |
| T-29 | A principal with `ssm:PutParameter` on `/application-plane/shared/identity/*` points `userPoolId` or `appClientId` at an issuer it controls before the demo stack is synthesised | The ingress trusts an attacker's issuer on the next deploy | **Accepted**: the demo resolves the parameters at deploy time (CloudFormation SSM parameter values), so a deploy reads whatever value the path holds then; nothing checks that the pool is tenant-identity's. The guard is account IAM on the shared parameter path, outside the sample; the construct itself reads no SSM, so a consumer wiring its own issuer is unaffected | M-20, M-1 |
| T-30 | A principal with `ssm:PutParameter` on `/application-plane/shared/agent-runtime/*` replaces `endpointUrl` or `runtimeArn` | A later consuming sample sends tenant tokens and prompts to an attacker's endpoint | **Accepted**: same guard as T-29; consumers are told to check the account in `runtimeArn` | M-20 |
| T-31 | A cdk-nag suppression relaxes a control without a stated reason, or the build's placeholder context reaches a real deployment | A mitigation believed present but absent | Mitigated by design | M-21 |
| T-32 | A bug or compromised dependency in the integration or interceptor Lambda runs code with the ingress role | `InvokeAgentRuntime` for any session, and with TVM `AssumeRole` on the tenant role with any tag: the one trusted principal turned against every tenant | **Accepted**: this is the pattern's cost (ADR-0001). The ingress is by design the one principal that can reach every session and every tenant's data role; pinned dependencies, refusal tests and CloudTrail detection bound it, nothing removes it. **Highest-consequence accepted item** | M-22, M-10 |
| T-33 | After an incident, a Runtime session, an `AssumeRole` or a Bedrock call cannot be attributed to a tenant | Isolation that cannot be shown to have held, nor billed or throttled per tenant | Mitigated: `tenantId` in ingress logs and metrics, session name `tenant-<tenant_id>` on `AssumeRole`, hash prefix on Runtime streams; what the Runtime cannot carry is listed in `architecture.md` | M-18, M-22 |
| T-34 | `cdk destroy` leaves the Runtime, a log group, the demo table or a parameter behind | Residual tenant data and a reachable Runtime in an account believed clean | Mitigated by design | M-23 |
| T-35 | One tenant's script uses up the shared stage throttle, the AgentCore Runtime session or TPS quota, or the account's Bedrock quota (narrows T-26) | Every other tenant gets 429s or throttling: a noisy neighbour in the pool | Mitigated by ADR-0020: a fleet-wide per-tenant request limit (60 per minute by default) and an optional output-token limit, checked before STS and the Runtime. **Residual accepted**: up to 2x the limit across a window boundary; fail-open on a DynamoDB error; no token limit on `agentcore-gateway` | M-25, M-19 |
| T-36 | TVM fan-out or a cold-start herd (many instances, many tag sets, `includeUserIdTag`) drives `sts:AssumeRole` past the account's 600 rps (narrows T-21) | Every tenant's request fails at the TVM | Mitigated by ADR-0022: a bounded LRU cache, one STS call per tag set per instance through single flight, and the ADR-0020 limit before STS. **Residual accepted** when an instance serves more active tag sets than `tvm.cacheMaxEntries` | M-26, M-25 |
| T-37 | A tenant forges or inflates another tenant's limit counter to lock it out | Another tenant limited (429) without having sent requests | Mitigated by design: the counter key is built from the verified `tenant_id` only, never from the request; only `tvmCallerRole` has `dynamodb:UpdateItem` on the table | M-27, M-1 |
| T-38 | Per-tenant metrics left on at many tenants (up to 9 custom metrics per tenant per ingress) | A CloudWatch bill that grows with tenants: with `TenantId` and `Ingress` dimensions that is 90,000 custom metrics at 10,000 tenants on one ingress; see [CloudWatch pricing](https://aws.amazon.com/cloudwatch/pricing/) | Mitigated by ADR-0021: off by default; a synth warning when on; the log line carries the same figures for Logs Insights and Contributor Insights | M-28 |

The residual (uncaught Lambda failure) is T-11 | P-2, [ADR-0002](./adr/0002-derive-the-session-id-from-validated-claims.md); `src/ingress/gateway-interceptor.function.ts`, the construct (`src/runtime-isolation.cdk.ts`, Gateway authoriser and interceptor wiring); `test/ingress/gateway-interceptor.function.test.ts` (thrown error → 403 short-circuit). ## Accepted risks

Listed in order of consequence. Each is on the README's production hardening
checklist unless marked "by design".

- **T-32, ingress compromise.** The ingress is the one principal the Runtime
  trusts and, with TVM, the one principal the tenant role trusts. That is
  what makes a leaked JWT useless (ADR-0001) and also what makes a bug in the
  integration or interceptor Lambda a boundary-wide bug. Pinned dependencies,
  one unit test per refusal, and CloudTrail alarms on any other principal
  calling `InvokeAgentRuntime` or assuming the tenant role bound it. Nothing
  removes it; a backend with native principal-to-unit binding would (ADR-0001
  "revisit").
- **T-16, tenant role trust widened by the deployer.** The construct grants
  only its half of the TVM contract. A `tvm.role` that trusts a second
  principal, drops the `TenantId` request-tag condition, or leaves
  `aws:TagKeys` open silently makes every tenant's data readable by anyone
  with `sts:AssumeRole`. The demo ships a correct role and the integration
  test proves the runner is refused, but the sample cannot validate a role it
  does not own.
- **T-11, Gateway interceptor fail-open on an uncaught failure.** In-code
  failures short-circuit to 403. What the Gateway does when the interceptor
  Lambda times out or is throttled is not documented and was not spiked,
  and the integration test has no throttle probe yet (follow-up). So
  `agentcore-gateway` carries a larger residual than `api-gateway`, and the
  README comparison says so (ADR-0009).
- **T-29, T-30, SSM parameter tampering.** Anyone with `ssm:PutParameter`
  on `/application-plane/shared/*` can repoint the issuer before a deploy or
  redirect a consumer. Shape checks at synth stop malformed values, not a
  swap for another real pool. The control is account IAM on the shared path.
- **T-26, T-35, noisy neighbour.** Pool model, one Runtime, one model quota.
  Since ADR-0020 each tenant has a fleet-wide request limit (60 per minute by
  default) on both ingresses, checked before STS and the Runtime. Residual: a
  tenant can reach up to twice the limit across a window boundary; a DynamoDB
  error admits requests (fail-open, so a DynamoDB fault is not an outage);
  `agentcore-gateway` has no output-token limit, because the interceptor never
  sees the response.
- **T-21, T-36, STS throttling through the TVM.** Since ADR-0022 the cache is
  bounded and concurrent misses share one STS call, and limited requests never
  reach STS. Residual: an instance serving more active tag sets than
  `tvm.cacheMaxEntries` calls STS more often; STS limits are per account and
  `includeUserIdTag` multiplies the key space. Size the bound to active
  tenants per instance.
- **T-38, per-tenant metric cost.** By design off; a deployer who turns
  `perTenantMetrics` on accepts up to 9 custom metrics per tenant per ingress,
  and the synth warning says so.
- **T-19, credential lifetime vs offboarding.** Vended credentials live up
  to `tvm.durationSeconds` (900 by default, 3600 at most) after the identity
  provider stops issuing tokens; recall needs a deny on the tenant role.
- **T-4, stolen token replay.** The token is the user for its 5-minute
  life; it reaches only that user's own units and data.
- **T-14, forwarded token in the microVM.** With `forwardUserToken` on, the
  agent holds a live token by design; redaction and the allowlist bound the
  exposure, the agent's code quality is the residual.
- **T-24, microVM isolation itself.** Service boundary; the sample ensures a
  breach gains nothing tenant-scoped beyond what the session already held.
- **T-23, `session.scope: 'tenant'`.** By design: an explicit trade, off by
  default.
- **T-28, session prefix as a pseudonym.** By design: the join to `tenantId`
  at the ingress is the attribution P-9 requires.
